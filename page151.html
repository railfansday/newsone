Your Agent's Context Fills Up Before You Type: What to Trim First

📅 Nov 04, 2026  |  Category: Technology  |  Read Source →

Most advice about coding agents is about what you type. But by the time you type your first prompt, the agent's context window is already partly full: instruction files, memory, tool names, skill descriptions. Then every file it reads, every test run and every long log adds more, and all of it is re-sent with every request.

That matters for more than your bill. In Effective context engineering for AI agents, Anthropic describes context rot: as the number of tokens in the window grows, the model's ability to accurately recall information from it goes down. Their framing is that a model has an "attention budget", and every token you add spends some of it. The guiding principle they give is to "find the smallest set of high-signal tokens that maximize the likelihood of your desired outcome."

I covered the money side in Where Your Coding Agent's Token Bill Goes. This one is about quality: what fills the context, and what to trim first so the agent has room to think about your actual task. The examples use Claude Code because its docs spell out exactly what loads and when, but the order works for any agent.

Don't guess. In Claude Code, run /context. The context window docs describe it as a live breakdown by category, with optimization suggestions, including which CLAUDE.md and auto memory files loaded.

Write down the three biggest categories. That's your trim list, in order. If you don't use Claude Code, the question is the same: what does your agent load at startup, and which of those things did you actually need today?

Anthropic calls bloated tool sets "one of the most common failure modes": too much functionality, or tools that overlap so the model can't tell which one to use. Their test is a good one to borrow: if a human engineer can't say for sure which tool fits a situation, the agent can't be expected to do better.

Claude Code already softens the cost here. Per its MCP docs, tool search is on by default, so only tool names and server instructions enter context at session start; full definitions load when Claude actually needs a tool. If you write your own MCP server, the docs suggest keeping descriptions and server instructions concise and putting the important words near the start, since that's the part tool search reads.

Instruction files load every session, whether the task needs them or not. Claude Code's memory docs recommend keeping each CLAUDE.md under 200 lines, and note that imports help you organise a long file but don't reduce its context cost, because imported files load with it.

Then look at what the agent reads during work. Vague prompts trigger broad scanning; the cost docs contrast "improve this codebase" with "add input validation to the login function in auth.ts". The second one lets the agent find what it needs with far fewer file reads.

Test runs, log files and documentation pages are the quiet context killers. A failing test suite can print thousands of lines when you needed ten.

Anthropic's post lists the same idea from the other direction: once a tool result is deep in history, the agent rarely needs to see the raw output again, and clearing old tool results is one of the lightest forms of compaction.

The longest-lived thing in your context is the conversation itself. You have two tools for it, and they do different things.

/clear when the task changes. Old conversation crowds out the files you need next and is re-sent with every message. The docs point out that /clear costs nothing, while /compact is itself a large request because it has to read the whole conversation it summarises. If you don't need continuity, clear. Use /rename first if you want to /resume that session later.

The logging setting that slows down new connections

📅 Nov 04, 2026  |  Category: Technology  |  Read Source →

Posted on Nov 4 • Edited on Nov 4 • Originally published at guardioz.com

The name log_hostname suggests that this setting puts the client address into PostgreSQL's server log. It does not: the address comes from %h in log_line_prefix. What log_hostname adds is a DNS lookup at the start of every new connection. We explain how the two settings work together, and we show what that lookup cost on PostgreSQL 18 when DNS was healthy, slow and down.

Three lines from one connection in our test. The log line prefix ends with %h, and the circled address is what %h prints: the IP address of the client that connected, not of the server. PostgreSQL logged it without any DNS lookup.

The server log can show where each connection came from. Two settings decide how, and they do different jobs.

The PostgreSQL 18 documentation describes log_hostname like this: "By default, connection log messages only show the IP address of the connecting host. Turning this parameter on causes logging of the host name as well. Note that depending on your host name resolution setup this might impose a non-negligible performance penalty."

Two details matter in practice. First, log_hostname adds no field of its own. Without %h - or %r, which adds the port - in log_line_prefix, ordinary log lines do not show the client at all, whatever log_hostname says, and the upstream default prefix, '%m [%p] ', has neither. The setting also changes the host= field of the "connection received" message, which appears when connection logging is on, and it fills the client_hostname column of pg_stat_activity. Second, in our tests the host name replaced the IP address in the log. It did not appear next to it.

A reverse DNS lookup asks DNS which name belongs to an IP address (a PTR record). With log_hostname on, PostgreSQL makes this lookup for every new TCP connection, right after the server process for that connection starts - before the client's first message is read and before authentication. The connection waits until DNS answers, or until the system's resolver gives up. Connections over a local Unix socket make no lookup.

The lookup runs whenever the setting is on, also when nothing in your configuration prints the name. Its time does not count against authentication_timeout, either. A comment next to the lookup in the PostgreSQL 18 source code says so directly: "PreAuthDelay and any DNS interactions above don't count against the time limit."

We measured the cost on two virtual machines in Microsoft Azure, in one private network: PostgreSQL 18.6 on Ubuntu 24.04 (Standard_D4s_v5, 4 vCPUs) and a separate client machine (Standard_D2s_v5). Connections used TLS 1.3 and SCRAM-SHA-256 password authentication, as many production setups do. The client ran pgbench, the benchmark tool that ships with PostgreSQL, with a one-line custom script (SELECT 1) and the -C option, which opens a new connection for every transaction. That makes connection setup most of the work, which is what this test is about. It is not a throughput test of a real workload.

Azure's DNS service answered the lookup for the client's address with the name vm-logtalk-hostname-cli.internal.cloudapp.net. Ubuntu runs a local DNS cache by default (systemd-resolved). Without such a cache, every lookup goes to the DNS server, so we tested the database server both ways.

For each setting, the table shows two numbers that pgbench prints at the end of a run. Connection time is how long it took, on average, to open one connection. Connections per second is how many times per second the client connected, ran SELECT 1 and disconnected; pgbench reports it as transactions per second, and with -C every transaction is one connection. With one client, each connection starts only after the previous one has finished, so the two numbers move in opposite directions: when every connection takes longer, fewer of them fit into a second. Connections per second here is the pace of a single client connecting again and again, not the most the server could accept.

Median of three 30-second pgbench runs per setting, run in alternating order: one client, a new connection for every transaction (pgbench -C), PostgreSQL 18.6 on Azure, Azure DNS answering normally. Connection time is pgbench's "average connection time"; the range shows the lowest and the highest of the three runs. Connections per second is pgbench's "tps (including reconnection times)".

Without a local cache, every new connection took about 6 ms longer: 43% more time per connection, and 29% fewer connections per second in this test. The server's own timing agrees. PostgreSQL 18 can log how long each connection took to set up (log_connections with the setup_durations option): the average grew from 10.4 ms to 16.3 ms, while the authentication part stayed at 6.0 ms in all three variants. The extra time is spent before authentication, where the lookup happens.

With the local cache, the difference was 0.3 ms. Azure DNS gave this answer a lifetime (TTL) of 10 seconds, so most lookups came from the cache. The 6 ms is what one round trip to Azure DNS cost from this server. On your network it is a different number: the time your DNS server needs to answer.

Healthy DNS is the best case. We then slowed DNS down, and then made it unreachable - only for the database server and only for DNS traffic - and ran the same test with one client.

One run per scenario: 30 seconds, 60 seconds for the run with DNS down and log_hostname on. One client, a new connection for every transaction, no local DNS cache unless the row says so. "DNS does not answer" means that the DNS server's answers never reached the database server, as in an outage. Connection time is pgbench's "average connection time"; in each run, the server's timing of the individual connections stayed close to this value.

With log_hostname off, DNS problems made no difference, because there was no lookup. With it on, every new connection waited for DNS. When DNS answered 100 ms late, each connection took about 109 ms longer. About 106 ms of that was the lookup itself: the 100 ms we added, on top of the 6 ms a lookup cost with healthy DNS. The remaining 2-3 ms were spread over the rest of the connection setup, and one run is not enough to explain them. When DNS did not answer, each connection waited until the resolver gave up: 20 seconds when the system resolver (glibc 2.39 on Ubuntu 24.04) asked DNS directly - it sent the question four times, five seconds apart - and 10 seconds through systemd-resolved. Resolver options can change these numbers, but not the pattern: a new connection takes as long as DNS takes to answer or to fail. With eight clients connecting at the same time and DNS down, the server completed 0.2 new connections per second. With log_hostname off and DNS healthy, the same eight clients completed 160 per second.

These are three lines from one of those 20-second connections, with %h in the log line prefix. The timestamp and process ID at the start of each line are replaced with ..., and long lines are wrapped:

When the lookup fails, PostgreSQL logs a WARNING and writes ??? in place of the client's host and port. The IP address the server already had does not appear anywhere in the log. It stays visible only in pg_stat_activity.client_addr, and only while the session is open. The last line also shows where the time went: 20 seconds of setup, of which authentication took 5.6 ms.

The cost does not depend on what you log. In one run we used the upstream default log_line_prefix and turned connection logging off, so nothing in the log could show a host name. Each connection still waited 20 seconds, and the only trace in the log was one WARNING line per connection.

With log_hostname on, PostgreSQL logs the name from the PTR record as it receives it. For the log, it does not check whether that name leads back to the same IP address. A PTR record belongs to the IP address, not to the domain in the name: it is set by whoever manages the reverse DNS for that address, usually the owner of the network the client connects from, or that network's provider. The owner of the domain in the name has no say in it. So whoever controls the reverse DNS of the client's address decides which name your log shows - even a name that looks like a different IP address.

We checked this on PostgreSQL 18.6 with a small DNS server that we controlled. We set the PTR record of the client address 127.0.0.5 to 10.0.0.5, and the PTR record of 127.0.0.6 to db-backup-01.corp.example, a name with no address behind it. These are five log lines from three connections. The log line prefix ends with %h; the timestamp and process ID are replaced with ..., and long lines are wrapped:

Every prefix and the "connection received" message show the name from the PTR record. In this test the real address appeared only in the text of a FATAL message, which PostgreSQL writes when it refuses a connection, and in pg_stat_activity.client_addr while a session was open.

PostgreSQL itself does not trust such a name for access control. A host name in pg_hba.conf matches only when the name also resolves back to the client's address, as the PostgreSQL 18 documentation describes. That is why the last connection was refused: our pg_hba.conf line for db-backup-01.corp.example did not match, because the name had no address. The log prefix showed the name anyway.

For an investigation, this means that a host name in the log is what the reverse DNS said, not proof of where a connection came from. With log_hostname off, %h logs the IP address the connection came from. If you need a name later, look the address up, and check that the name resolves back to the same address - the check that pg_hba.conf makes and the log does not.

The lookup happens once per connection, not once per query. In one 30-second run per setting with eight connections that stayed open, the server answered 19,291 queries per second with log_hostname off and 19,165 with it on. One run per setting cannot show whether a 0.7% difference is real, but the mechanism explains why it should be small: once a connection exists, it makes no more lookups.

This is why a connection pool can hide the setting for a long time. The cost comes back when the pool opens new connections - for example after a database restart or a failover, when every connection in the pool is opened again at about the same time, and each one makes its own lookup.

Sometimes a name is useful - for example, when client IP addresses change often and you keep logs for a long time. In that case, resolve the addresses when you read the log, not while clients wait to connect: an IP address in the log can be looked up later, during an investigation. Keep in mind that the answer then reflects DNS at the time you ask, not at the time of the connection.

Two more notes. Behind a connection pooler, %h shows the pooler's address, whatever log_hostname says. And to see which application a log line belongs to, use application_name: the client sets it, %a prints it, and it needs no lookup.

Reaching Full Retirement Age for Social Security in 2027? Here's Why You May Not Want to File Just Yet

📅 Nov 04, 2026  |  Category: Business  |  Read Source →

Taking benefits right away isn't your only option.

If you'll be turning 67 in 2027, you should know that you'll be hitting a big milestone in the context of Social Security. Age 67 is Social Security's full retirement age. That's when you can collect your monthly benefits based on your earnings history without a reduction.

The earliest age to claim Social Security is actually 62. But for each month you take benefits before reaching full retirement age, those monthly checks are reduced. So if you were born in 1960 or later, waiting until 67 to claim Social Security can be a smart move.

But that doesn't mean you should rush to claim Social Security next year if you'll be turning 67. You may find that waiting makes even more sense.

While full retirement age is when you get your Social Security checks without a reduction, delaying your claim past that point boosts your monthly benefits by 8% a year for life. And while this incentive does run out at age 70, if you hold off on filing for three years, you can boost your Social Security benefits by 24%.

Imagine your full retirement age benefit is $2,000 a month. Waiting until age 70 to file gives you $2,480 per month instead. And that's not the only perk.

Each year, Social Security benefits are eligible for a cost-of-living adjustment, or COLA. If you boost your benefits by waiting past full retirement age to file, each COLA that comes through will be worth more money to you by virtue of having a larger monthly baseline check.

Also, if you're the higher earner in your household and your spouse outlives you, they'll typically be entitled to survivor benefits from Social Security after you pass away. The larger your benefits are, the more money your spouse stands to collect.

If 2027 is the year you'll reach full retirement age for Social Security, you may be inclined to take benefits at that time. But there's a lot to be gained by waiting longer to file.

Even if delaying your claim until age 70 isn't feasible, holding off for a single year results in an 8% boost. And a smaller increase could help your retirement finances, too.

Remember, the more Social Security pays you each month, the less pressure there is on your savings. Keep that and the points above in mind when your 67th birthday arrives so you don't make a filing decision you regret.

Shopify Stock Fell After Its Report. Here's the Price I'd Pay for It.

📅 Nov 04, 2026  |  Category: Technology  |  Read Source →

The e-commerce company's free cash flow climbed 61% last quarter, but the stock fell anyway. Is it cheap enough now?

Shopify (SHOP -8.74%) stock fell nearly 9% on Tuesday after the e-commerce software company posted its third-quarter results. At roughly $144 as I write, shares are about 20% below their Oct. 12 record close of $179.22.

The slide came even though revenue climbed 32% year over year to about $3.7 billion and free cash flow jumped 61% to $816 million.

Before the report, I wrote that I'd rather wait and see where shares settled afterward. The stock was around $157 then, or about 86 times its trailing free cash flow. Now the cash flow has come in slightly over the $800 million I'd penciled in for a strong quarter, and the price is lower. Is it finally time to buy?

Investors seemed to want more than a quarter that landed where management said it would. Shopify's guidance was for third-quarter revenue growth in the low 30s, and 32% delivered that.

But revenue had grown 34% in each of the two previous quarters, beating a low-thirties outlook for the first quarter and a high-twenties forecast for the second.

Gross merchandise volume (GMV, the value of orders placed on Shopify's platform) slowed, too. It rose 29% to $119 billion in the third quarter, after gaining 35% in the first quarter and 32% in the second. Currency explains most of that. In constant currency, GMV grew 30% in all three quarters. Gross profit, though, is where the slowdown shows. Its growth rate dipped to 28% in the third quarter, under the 32% and 31% rates in the first two quarters. And management sees high-twenties growth again in the fourth quarter.

Spending is also set to rise. Management guided fourth-quarter operating expenses to 29% to 30% of revenue. In the fourth quarter of 2025, they were about 29%. Chief financial officer Jeff Hoffmeister said on the call that the forecast reflects more marketing, including some efforts before Black Friday and Cyber Monday. A U.S. marketing test held down spending in the third quarter, and he said part of that spending will move to the fourth.

Taking the middle of each range in the guidance, I get fourth-quarter operating income growth in the high teens. That means profit growth might slow sharply from the 66% Shopify just reported.

I doubt any of these explains Tuesday's fall by itself. But together, they suggest profit growth may ease in the quarters ahead.

Shopify's free cash flow margin (the part of revenue left as cash after capital spending) was 22%, against 18% in the third quarter of 2025. This pushed trailing-12-month free cash flow to around $2.7 billion, up from nearly $2.4 billion through June.

Between the higher cash flow and the lower price, the stock's valuation looks much less stretched than it did last week. At a market cap of around $185 billion, Shopify now trades at about 70 times trailing free cash flow, against about 86 times free cash flow before the report and about 98 times free cash flow at the Oct. 12 record.

Still, not all of that improvement is likely to last. Hoffmeister said only about 1.5 percentage points of the margin gain came from lasting cost discipline. He called the rest more temporary, spread about evenly between the marketing test, the timing of some tax receivables, and an accounting change that shifted merchant cash advances (Shopify's financing for its sellers) out of operating cash flow. Management also expects the fourth-quarter free cash flow margin to roughly match last year's 19%.

Taking out the temporary piece, third-quarter free cash flow would have been closer to $725 million. That comes out to around 72 times trailing free cash flow, just slightly above 70.

Yes, the e-commerce company is still growing quickly and bringing in much more cash than it did a year ago. Shopify even spent $562 million of that cash to buy back its own shares in the third quarter.

But at around 70 times free cash flow, buyers are still paying for years of rapid growth. And they're paying it right as gross profit growth cools and management boosts its marketing.

Does the lower price make Shopify a buy? I think the drop moved the stock closer to a price I'd pay, but not all the way there. I'd start to consider shares somewhere around $115, or about 55 times trailing free cash flow.

That's about 20% under where the stock sits now, so I'm in no rush.

Dirk Kuyt, Liverpool’s big-game hero and embodiment of the Benitez era

📅 Nov 04, 2026  |  Category: Sports  |  Read Source →

English fans can be excused for never been quite sure what to expect when a striker swaps the Eredivisie for the Premier League.

Will they be the next Robin van Persie or Ruud van Nistelrooy? Or are they being sold false goods? Think Ricky van Wolfswinkel. A star in Holland with Utrecht and then in Portugal with Sporting but the scorer of precisely one goal in England during a full season with Norwich.

Dirk Kuyt had plundered 71 goals in 101 games for Feyenoord before Liverpool pressed ‘buy’ in the summer of 2006. In theory, the Reds were getting a bargain at just £10million. A proven goalscorer and, those who had seen him in action, the very antithesis of a goal hanger.

Yes, Kuyt ran around a lot. He worked for the team. He put in a shift. Ironically, that was part of the reason why his career at Liverpool will be remembered as that of honest pro rather than superstar.

Kuyt, with those solid legs and neat mop of blonde hair, made his debut in a 2-1 home win over West Ham on August 26, 2006, coming on as a substitute to replace Peter Crouch.

That 2006-07 Liverpool team could be classed as being ‘between strikers’.

Crouch brought something different to the mix and Craig Bellamy was a classy pest with a goal or two in him, while Robbie Fowler had come back for a second stint but was more nostalgia act than genuine first-teamer so there was a goalscoring void to be filled. Was Kuyt the man?

This, of course, was the Rafa Benitez era at Anfield. His tactical wizardry had guided a genuinely mixed bag of a Liverpool team to Champions League glory in 2005, but now there was the Holy Grail of trying to win the Premier League.

Anyone and everyone can chip in on cup runs, but a title assault needs a genuine and regular goalscorer. A 20-goal haul from Kuyt and solid contributions from elsewhere could have been the winning formula.

The Dutchman took a little while to settle but scored twice in four days at the end of September, helping Liverpool to home wins against Newcastle and Spurs.

Reds fans were hopeful but cautious too. On the one hand, there was a feeling that could this be the start of something. On the other, there was a nagging feeling that he was good but not great. A seven out of 10 player.

Fans are greedy. They want superstars. They want No.9s and No.10s. Kuyt looked like what he was. A £10million signing from the Dutch league.

He scored 14 goals in that first campaign, a very respectable haul but not a game-changing one.

In the next, he managed 11 while a late flurry in Liverpool’s near-miss 2008-09 season yielded 15.

It was back to 11 in the following campaign but back up to 15 in 2009-10, a tally boosted by one very special afternoon against Manchester United.

One thing was very clear. Rafa loved him. Or rather, given that the Spaniard doesn’t really do love, Rafa saw how valuable he was to the cause. From being an out-and-out striker, Benitez turned Kuyt into the ultimate workhorse, ploughing a furrow up and down one side of a front three.

And Liverpool fans adjusted with him. The fanciful expectations of Kuyt being a world-beater had been downgraded to a different type of admiration. He wasn’t Pele, but good old Dirk would play his heart out for the club and die for the cause. And that goes a long, long way on Merseyside.

While other Reds flickered and flirted with greatness, Kuyt offered a rubber-stamped guarantee. Whatever the occasion, whatever the opponent, whatever the location, he would put in a blue-collar shift week in, week out.

That can sound patronising, but Kuyt had another trick up his sleeve which moved him into a category beyond honest trier. The man from the little coastal town of Katwijk aan See (Dutch for Clacton-on-Sea… well, not really) could score big goals in big games.

When he finally left the Big Anfield House in 2012, his ‘best bits’ were quite something:

– Scorer in the 2006-07 Champions League final against AC Milan

– Scorer of the winning penalty in the 2007 semi-final second leg against Chelsea.

– First player in 21 years to score a hat-trick against Manchester United

– Injury-time penalty to secure dramatic derby win at Everton

– Extra-time goal against Cardiff in the 2012 League Cup final

– Shootout goal against Cardiff to secure League Cup final glory

There were other important strikes against Arsenal, while he netted seven times in the 2007-08 Champions League campaign. Even the hat-trick against Manchester United had added cult value as they were all one-yard tap-ins. Those goalscoring instincts had never left him.

Not many can claim to have scored a hat-trick against Manchester United.

In many ways, Dirk Kuyt was the embodiment of the Benitez era. Tactically astute, hard-working and capable of taking it up a level on big occasions.

You don’t build a football team just by throwing 11 superstars together. Even Brazil 70 had a few in their ranks who provided solidity and balance. That was Dirk Kuyt at Liverpool. Popular, reliable and hugely valuable.

Imagine Kuyt was at his peak now. Would he make this current high-flying Liverpool team? Not as a regular starter, but Jurgen Klopp would have him as a squad player all day long.

Slight injury concern for one of the litany of superstar forwards in the squad? Two games in four days? Tough away assignment where you need to dig in but try to nick a big goal?
