Securing Your Agents: A Hands-On Guide to Agent Anomaly Detection

📅 Nov 17, 2026  |  Category: Technology  |  Read Source →

As highlighted in our announcement post, we said that each new model generation lets agents do more on their own. However, the more an agent can reach, the more one bad decision can cost. You've probably seen a few of these in the news lately:

Because these events produced no system crashes or logging errors, the teams behind these agents had no way to know until the damage occurred.

Agent Anomaly Detection on the Gemini Platform watches for exactly these issues. It reads the traces and logs your agents already produce and flags sessions where an agent goes outside the job it was built for.

Before you point it at your production agents, you'll probably want to see it work in a test environment. In this hands-on guide, we’ll walk you step-by-step through setting up Agent Anomaly Detection and using it to capture your very first agent behavior anomaly. By the end of this post, you'll have:

To get started, open the companion notebook Detect anomalous agent behavior with Agent Anomaly Detection in a separate tab (available on Google Colab or GitHub). As you read through this guide, it will prompt you when to execute notebook cells or interact directly with the Google Cloud console.

If a step can be done in the UI console, this post shows that path, with screenshots. The notebook does the same thing through the Agent Anomaly Detection API, so by the end you'll also have the code to automate enablement and pull findings into your own tooling.

2. A place to run the notebook: Google Colab, Colab Enterprise, or a local Jupyter environment. The notebook installs the latest ADK for Python itself. Agent Anomaly Detection is compatible with agents running ADK 1.2+, though ADK 2.0+ is preferred for best results.

3. A Cloud Logging bucket and an Observability dataset in either US or EU multi-region. (Both resources need to be in the same multi-region)

4. In the notebook: run the Get started cells. They install the packages, authenticate you, take your project ID, and turn on the four APIs that Agent Anomaly Detection needs.

First, let’s create a Customer Support Agent called “anomaly-detection-refund-demo”. Our example agent is responsible for helping customers check their order history and request refunds. All three parts of the lethal trifecta are here: the agent can read private data, it takes input from people it can't vet, and it sends what it finds back in its reply. Tool permissions and guardrails should stop most of this, but they only block what someone thought to write down. Agent Anomaly Detection flags the sessions that get past them, usually within a few minutes.

Click an invocation in the Session pane to see its analysis in Details. Each invocation is Medium on its own, but together they make the session High.

To stay informed without watching the console, connect Agent Anomaly Detection to your existing alerting workflows.

In Cloud Monitoring: Agent Anomaly Detection publishes two metrics: Detected events, which counts anomalies by detector and severity, and Monitored agents, which tracks your detection coverage. To view these metrics, click the arrow next to "View in Cloud Monitoring" on the Anomaly detection page and select a metric to open it in Metrics Explorer.

To be notified of new anomalies, go to Monitoring > Alerting, click "Create policy", and select the Detected events metric. Leave the filters empty so the alert covers every anomaly, including the demo's, then set the rolling window to 5 minutes with the delta function, and set the threshold to above 0. Once you know what's normal for your agents, add a severity filter (for example High or Critical) so you're only alerted on the findings that matter. A metric-absence policy on Monitored agents will also alert you if monitoring stops.

In Security Command Center: Each anomaly is also published as an AGENT_SESSION_ANOMALY finding in the Security Command Center if it is enabled for your organization. Click "View in Security Command Center" to triage these findings alongside your other threats, use "Set security marks" to tag and track them, and set up notifications for high-severity findings.

You’ve now seen Agent Anomaly Detection in action: it successfully flagged the session where our agent went off-script to read payroll records, while evaluating the benign session, and correctly not flagging an anomaly. The finding told you why it was flagged and how to fix the underlying issue, and alerts in Cloud Monitoring and Security Command Center ensure you are notified of future anomalies.

TPU Model Design Considerations and Optimization Guide

📅 Nov 17, 2026  |  Category: Technology  |  Read Source →

Google designed TPUs from the ground up to be exceptionally efficient for machine learning workloads, delivering top-tier performance per total cost of ownership (TCO). Because TPUs trade general-purpose hardware scheduling for wide systolic arrays, dedicated SparseCore engines, and custom interconnect fabrics, adhering to specific architectural best practices is essential to achieve maximum performance. To help developers get the most out of TPUs, we are launching the open-source AI-Hypercomputer/tpu-codesign guide. This post highlights its key principles—spanning shape alignment, architectural choices like LatentMoE, and parallelism strategies—to accelerate LLMs, Mixture-of-Experts (MoE) models, and other hardware-intensive workloads on TPUs.

Performance tuning starts with model definition. Architectural choices made before the first training step set permanent ceilings on MFU (Model FLOP Utilization), cost, and serving latency. This guide gives concrete, hardware-grounded design rules for teams building or adapting models for TPUs, organized into three groups:

How to use this guide. The shape rules apply to anyone designing a new model. If you are adapting an existing model rather than designing one, the Expressing Parallelism section applies without touching the checkpoint. The general rules hold for any large-matmul architecture (dense LLMs, multimodal, and world models), and the companion AI-Hypercomputer/tpu-codesign repository grows model- and workload-specific sections over time.

Eighth-generation TPUs. These principles carry forward to TPU 8t and TPU 8i and to the newly announced TPU 8tx and TPU 8i Max. The reasoning stays the same and the thresholds move with the hardware. TPU 8t and TPU 8i both add native FP4. For training, TPU 8t also brings more balanced Vector Processing Unit (VPU) scaling. For serving, TPU 8i adds the Boardfly topology, a Collectives Acceleration Engine (CAE), and 3x more on-chip SRAM. We note the effects inline in Principles 5–8, and follow-up posts will cover eighth-generation designs in depth.

Measured evidence. Alongside the published sources, notes marked Measured carry results from our own Ironwood profiling program: open 20–30B MoEs (a Qwen3-30B-derived LatentMoE variant; GPT-OSS-20B) plus dense controls, single slice (except for the 512-chip TPU v7x and 1,024-chip TPU v4 ablations in Principle 4), BF16, training shapes up to 32K sequence, all against tuned-systems baselines. Treat the trends and rankings as transferable, the exact percentages as config-specific.

TPUs are purpose-built custom ML ASICs designed from the ground up to deliver state-of-the-art performance per total cost of ownership (TCO). While their architectural choices—such as wide 256×256 systolic arrays, software-managed VMEM, dedicated SparseCore engines, and direct multi-dimensional ICI fabrics—enable exceptional efficiency, they inherently create specific structural constraints and programming patterns that must be carefully followed to unlock maximal performance. Reaching peak efficiency requires aligning model shapes, routing, and parallelism directly with these underlying hardware characteristics:

Make d_model, FFN and expert intermediate widths (d_ff), latent widths, attention projections, and padded vocabulary sizes (used as contracting or output dimensions) multiples of 256 to match the 256×256 MXU systolic array. Token/batch axes and counts such as heads, layers, and experts are exempt. The most frequently missed dimension is head_dim: at 64 or 128, flash-attention QK products leave the MXU ≥ 50% idle. Reshape to head_dim = 256 with proportionally fewer Q and KV heads, preserving total projection widths and logical KV cache bytes (iso-quality in our ablations).

Measured: Reshaping Qwen3-30B MoE attention from 32 × 128 to 16 × 256 (identical parameters and FLOPs) sped up end-to-end training, with gains widening at longer context:

These rules apply for non-quadratic attention as well, notably GDN ablations from Yang et al. 2025 also noted at par or better quality for head dimension 256 for their Gated DeltaNet Attention.

XLA compiles each program for exact tensor shapes, so every buffer has a fixed address and every loop a known trip count, and a new shape means a recompilation and a host stall. What about dynamic shapes? Dynamic workloads fit this model: the trick is to separate the shape of a buffer from the extent of the data inside it.

Instead of padding to the largest group or the longest sequence, we keep the buffers at fixed shapes (tokens sorted by expert and padded only at the tail, the KV cache as a fixed pool of pages) and describe the ragged structure with a few small integer arrays (group sizes and offsets; KV lengths, the page table, cumulative query lengths). Pallas copies these into the TensorCore's scalar memory before the grid starts (PrefetchScalarGridSpec), and the kernel reads them to choose the next tile and bound its loops, with a mask covering a tile that straddles a group boundary or a partly filled last page. The data dependence becomes an address and a trip count instead of a shape, so the compiled program is the same for every routing and every batch composition and the kernel runs at the unpadded FLOP count.

Standard EP dispatches every routed token at full d_model width, making EP + FSDP slower than plain FSDP in our Ironwood benchmarks. LatentMoE projects routed tokens from d_model down to latent width ℓ (d/ℓ ≈ 2–4×) before dispatch, executes experts in latent space, and projects back up after combine (introduced by Nemotron 3 and adopted by 962B MAI-Base-1 and 2.8T Kimi K3):

Measured: On a 30B / 128-expert MoE, an ℓ = 768 (2.67×) LatentMoE cut on-device permute time 2.8×, lifted end-to-end training throughput +14% tokens/s (322 vs 270 TFLOP/s/chip, or +19%, since the latent projections add ~5% FLOPs per token; tokens stay ℓ-wide past the down-projection, so on-device permute and combine shrink alongside EP all-to-all), and freed ~25 GB/device of activation HBM when remat checkpoints were anchored on the compressed latent. While current MoE recipes in tpu-recipes run FSDP (+ TP), LatentMoE + FP8 dispatch makes EP roofline-viable when per-device batch is too small to hide FSDP weight all-gathers. Under both FSDP and EP, avoid over-fragmenting experts: small tokens × K / N group sizes starve MXU tiles.

When candidate MoE layouts match on quality, pick the one with higher compute intensity at a similar active-parameter budget. A larger shared expert (wider d_shared) shifts work into dense, communication-free GEMMs that overlap EP dispatch/combine in training and amortize weight reads across the decode batch. Fewer, wider routed experts (halving N and K while doubling d_ff at fixed sparsity K/N) cut dispatch traffic in half and double per-expert GEMM fill. Optimal (N, K) grows with model size, and over-coarsening hurts routing diversity. Ablate expert granularity and the shared-to-routed split at your target scale rather than copying GPU co-designed models, since the TPU optimum is more shared-heavy.

Measured: On a 63B LatentMoE (ℓ = 768, K/N = 1/32, 8K context, 512 TPU v7x chips at EP = 128), halving (N, K) from (512, 16) to (256, 8) while doubling d_ff and the shared expert lifted training throughput +57% tok/s and held lower loss across 120.8B tokens:

Low-concurrency decode streams model weights every token (~300 concurrent tokens per weight shard are needed in dense FP8 to reach compute roofline). Combine two architectural levers with explicit concurrency sizing:

Norms, activations, masking, routing math and quantization scale applies run on the Vector Processing Unit (VPU), which is roughly two orders of magnitude below the MXU in throughput and executes in sequence with the matmuls unless XLA fuses it into an adjacent GEMM or we move it off the TensorCore. Therefore we drop reshapes and transposes that carry no quality, standardize on fusable RMSNorm and SwiGLU so the elementwise work folds into the neighbouring GEMM, and offload the MoE sort, gather and scatter to the SparseCore.

Note that fused VPU work is free only while its cycle count fits inside the MXU window it is fused into. A quick illustration of this concept is block-scaled fp8 GEMM.

With a scale per block of B elements along the contraction axis, the MXU emits one partial sum per output element per block and the VPU rescales each one (about three vector ops), so per output element the MXU does 2K flops and the VPU does 3·ceil(K/B) ops. The rescale hides when B ≥ 1.5 × r_mxu / r_vpu, which on v7x (fp8 peak 4,614 TFLOPS against a 19.2 TFLOPS vector peak, a ratio near 240) puts the threshold near 340. In simulation on a DeepSeek-V3 expert shape, block 512 runs at the per-tensor time, block 256 is VPU-bound at 1.2x and block 128 at 2.4x. Achieved MXU efficiency is lower than peak, which lowers the effective ratio and can make the smaller blocks workable; the way to decide is to measure the GEMM at each block instead of using peak ratio. This threshold is specific to Ironwood. TPU 8t is designed with specialized support for scaling so quantization for MXFP4 and MXFP8 formats has no overhead. Re-measure the block-size threshold there instead of reusing 340. The rule itself carries forward: keep vector work hidden inside a matmul window.

For workloads dominated by BF16-sensitive matmuls (most notably long-context quadratic attention where direct FP8 degrades accuracy), native single-pass BF16 leaves MXU capacity unused whenever hardware low-precision MXU throughput exceeds native BF16 throughput by more than the pass count. Use the multi-pass BF16 algorithm to execute BF16-accurate matmuls via multiple passes over the higher-throughput lower-precision MXU pipeline without losing numerical fidelity. This matters more as low-precision throughput pulls ahead of BF16. TPU 8t adds native FP4, which doubles MXU throughput. On Ironwood the FP8 to BF16 ratio is exactly 2:1, so two or more passes cannot beat native BF16.

Assign communication-heavy parallel axes to the fastest physical links and keep logical mesh factors aligned with torus dimensions:

Minimum-degree CP matched to kernel trade-offs: All-gather CP is simplest (though its all-gathers can sit exposed) when paired with zigzag load balancing (context_parallel_load_balance in MaxText) so causal masking does not idle tail ranks; Ring CP overlaps collectives but trades off SplashAttention chunk efficiency; Ulysses A2A CP avoids causal skew but exposes all-to-alls and caps at head count.

Start every project with the quality-safe foundation: 256-aligned dimensions (1), static shapes with dropless routing (2), one parallelism plan mapped to physical links (8), wall-clock ablations on a tuned stack, and published reference targets (both in Measuring what matters below). For MoEs, add LatentMoE (3) after an ablation to cut routing/dispatch traffic and decode weight reads. Then prioritize by bottleneck regime:

Google engineered TPUs from the ground up as custom ML ASICs to deliver top-tier performance per total cost of ownership (TCO). Unlocking that potential requires bridging the gap between hardware architecture and model design. By standardizing on 256-aligned shapes, leveraging LatentMoE, and mapping parallel axes directly to physical links, engineering teams can maximize TPU efficiency across both training and serving workloads.

A reference blueprint is only as good as the loop used to validate it. Always evaluate architectural changes in wall-clock time on a tuned software stack rather than paper FLOPs: in our Ironwood benchmarks, pure systems tuning (SparseCore offload, MXU-aligned tiles, and remat tuning) lifted an open 30B MoE from 12% to 23% MFU before any model change, and published Ironwood baselines show 256-aligned MoEs (DeepSeek-V3, Qwen3-235B at 608–630 BF16 TFLOP/s/chip) running at roughly 2× the throughput of unaligned GPT-OSS-120B (330 TFLOP/s/chip). For the 6-signal XProf (profiler=xplane) triage checklist, roofline and HBM budgeting rules, wall-clock ablation methodology, published Ironwood reference targets, and ongoing updates as new TPU generations and kernels land, explore the living diagnostics guide and companion patterns in the open-source AI-Hypercomputer/tpu-codesign repository.

Thermal camera vs optical gas imaging on a robot dog: what each can and cannot detect

📅 Nov 17, 2026  |  Category: Technology  |  Read Source →

Posted on Nov 17 • Originally published at yuanzhirobot.com • AI-assisted

Short answer: A standard thermal camera measures surface temperature and finds overheating equipment, but it cannot see most gas leaks. An optical gas imaging (OGI) camera is a filtered infrared camera tuned to the absorption band of specific gases, so it shows leaks as a visible plume; it is heavier, costlier and qualitative unless extra quantification is added.

By the engineering team at YUANZHI ROBOTICS. We design and build sensor payloads for robot dogs, UGVs and drones. Originally published on our site; AI-assisted draft, reviewed by our engineers.

A standard thermal camera and an optical gas imaging (OGI) camera both work in the infrared, but they answer different questions. A thermal camera tells you how hot a surface is, so it finds overheating joints, bearings and motors. An OGI camera is filtered to the narrow band where a particular gas absorbs infrared, so it makes a leak visible as a moving plume. A thermal camera will not reliably show a gas leak, and an OGI camera is not the right tool for measuring equipment temperature. This guide explains the difference and how we decide what goes on a robot dog.

Thermal view separating a warm target from a cooler background: thermal cameras image surface temperature, not gas

Most thermal cameras used on robots are uncooled microbolometers working across the long-wave band, roughly 8 to 14 micrometres. They integrate energy over that whole band and convert it to a temperature for each pixel. That is exactly what you want for electrical and mechanical inspection: a loose busbar joint, a failing bearing or a blocked cooler shows up as a temperature difference against its neighbours, and a radiometric core lets the software store a number for each inspection point and compare it over time.

Most gases are almost transparent across that wide band, or absorb only in a narrow slice of it. Averaged over the whole band, a thin plume barely changes the reading, so on a normal thermal image the leak is invisible. Sometimes you see side effects, such as frost where expanding gas cools a fitting, but you cannot rely on that for leak detection.

An OGI camera puts a narrow band-pass filter in front of the detector, matched to an absorption band of the target gas. Gas in the field of view now absorbs or emits a noticeable share of the energy the camera sees, so it appears as a dark or light cloud against the background. Two families matter in practice:

One OGI camera does not see every gas. The camera is chosen for the gas list of the site, which is why we ask for that list before anything else.

Thermal options span a wide range on the same robot, and the choice is mostly about resolution, optics and whether you need pan-tilt. From the components we integrate:

An OGI camera has to be added on top of this budget. On a Unitree Go2 class robot that is rarely realistic; on a Unitree B2 or DEEP Robotics X30 it can be, after the weight and power budget is checked. Our payload weight budget guide shows how we do that.

Unitree B2 with a YUANZHI ROBOTICS sensor payload (3D render): heavier quadrupeds leave room for a gimbal and extra gas sensing

For substations and power plants the common set is a dual-spectrum thermal and zoom camera for equipment temperature and gauge reading, plus point sensors for the gas list, for example an NDIR SF6 module such as the Cubic SF6-015 (about 0.65 W) with electrochemical O2, CO and H2S cells. Point sensors give a concentration and an alarm threshold; they do not show where the leak is. Our gas detection payload guide covers sampling and calibration, and the substation payload guide shows the full set for that site type.

For oil, gas and chemical sites where locating hydrocarbon leaks is the main task, we add either a laser methane detector, which measures along a beam at a distance, or an OGI camera on a heavier robot, and keep the thermal camera for rotating equipment. Using point sensors to confirm what the image shows is more robust than relying on either alone.

Optical gas imaging view of a leak plume during a robot dog patrol: the gas itself becomes visible, but not its concentration

Send us your gas list, the equipment you need to measure and your robot model, and we will propose a thermal, gas and camera set that fits its payload limit. You can start in the payload configurator, look at the Unitree B2 or DEEP Robotics X30 platform pages, or read about our inspection robot and robot payload services.

Can a normal thermal camera on a robot dog detect gas leaks?

Generally no. A broadband 8-14 micrometre thermal camera shows surface temperature. It may hint at a leak indirectly, for example frost on a valve from expanding gas, but it does not image the gas itself. Seeing the gas needs an optical gas imaging camera filtered for that gas, or a point or laser gas sensor.

It depends on the filter. Cooled mid-wave OGI cameras are built for hydrocarbons such as methane, propane and VOCs. Long-wave OGI variants target gases such as SF6, ammonia and some refrigerants. One camera does not cover all gases, so the camera is chosen for the gas list of the site.

Does optical gas imaging tell you the concentration?

Not by itself. OGI shows where gas is and how the plume moves. Concentration or leak rate needs a quantification method with known distance, temperature contrast and wind, or a separate sensor such as a laser methane detector or a sampled point sensor.

Should I put both a thermal camera and gas sensors on one robot dog?

For most electrical and plant patrols, yes: a dual-spectrum thermal and zoom camera for equipment temperature, plus point gas sensors for the site gas list. Add an OGI camera only where finding hydrocarbon or SF6 leak sources visually is a core requirement, because it adds weight and cost.

GBase Database: What Do profile, onconfig, and sqlhosts Actually Do?

📅 Nov 17, 2026  |  Category: Technology  |  Read Source →

When initializing GBase Database(GBase 8s), three configuration files are easy to confuse: profile, onconfig, and sqlhosts.

All three may include the instance name as a suffix, but they serve completely different purposes.

Confusing them can send database troubleshooting in the wrong direction. Understanding their responsibilities is essential for database initialization, configuration management, and connection troubleshooting.

The easiest way to understand these files is to separate their responsibilities:

These files work together, but they are not interchangeable.

This file establishes the environment variables required by GBase Database.

This file defines instance-level configuration.

Production configurations contain additional parameters, including memory, buffer pool, and lock settings.

This file defines the connection entry for the instance.

For remote connections, the IP address, port, protocol, and corresponding listener configuration must agree.

The relationship can be understood as a simple configuration chain:

The profile establishes the environment, onconfig controls instance behavior, and sqlhosts provides connection information.

A mismatch in any of these layers can cause startup or connectivity problems.

The troubleshooting sequence should follow the responsibility of each file.

Check the instance name and configuration paths:

Then verify that the referenced files actually exist:

Check whether ROOTPATH points to the intended location and whether the required directory or device exists with the correct ownership and permissions.

Case B: The instance starts, but remote clients cannot connect

Then check whether the database listener is running and whether the port is listening:

Arquitectura proporcional: no construyas un e-commerce para resolver una mudanza

📅 Nov 17, 2026  |  Category: Technology  |  Read Source →

Posted on Nov 17 • Originally published at juliancardozo.github.io

Publicado originalmente en juliancardozo.github.io.

Casa Médanos resolvía una necesidad acotada en tiempo: publicar, compartir y mantener disponible un inventario de muebles y electrodomésticos antes de una mudanza. El criterio de arquitectura fue operativo: eliminar trabajo manual y costo de mantenimiento, no anticipar capacidades de una plataforma de e-commerce que el caso no requería.

La tentación técnica era conocida: cuentas, pagos, carrito, backend, inventario. Pero el problema tenía una fecha concreta. Cada semana que pasaba importaba más publicar el catálogo que diseñar una plataforma capaz de sobrevivir diez años.

Esa restricción ordenó la decisión. Casa Médanos se convirtió en un catálogo rápido y compartible: fotos, precios visibles, filtros por ambiente, buscador y un estado claro para lo vendido. Un único link reemplazó una cantidad absurda de mensajes repetidos.

Elegir un sitio estático en GitHub Pages no fue recortar funcionalidad por deporte. Fue sacar de escena servidores que monitorear, bases que respaldar y costos que no ayudaban a vender un sillón. Para quien llega desde una red social, además, una página que carga rápido resuelve más que una arquitectura sofisticada.

La complejidad quedó donde sí había trabajo real: actualizar disponibilidad, encontrar un artículo y mostrar que algo ya se vendió sin hacerlo desaparecer. La tecnología siguió al flujo, no al revés.

Las preguntas repetidas justificaban una automatización puntual. Un flujo de n8n, versionado junto al código, ayuda a responder sin inventar una aplicación de mensajería ni convertir una venta temporal en una operación permanente.

Desde entonces uso una prueba sencilla: si una pieza de infraestructura no reduce una tarea repetitiva, un riesgo real o un costo presente, todavía no pertenece al MVP. Puede llegar después. Hoy solo distrae.

Principio de arquitectura: la solución debe responder a la vida útil, el riesgo y el volumen del problema actual. Toda capacidad extra también agrega costo operativo.

Del problema observado al MVP: diseñar producto desde el trabajo real del usuario

📅 Nov 17, 2026  |  Category: Technology  |  Read Source →

Posted on Nov 17 • Originally published at juliancardozo.github.io

Publicado originalmente en juliancardozo.github.io.

EscalaImprov comenzó con una necesidad observable: transformar teoría musical en decisiones inmediatas durante una jam. El caso ilustra una práctica de producto aplicable a cualquier negocio: partir de una fricción concreta, validarla como patrón y diseñar flujos distintos para los trabajos que el usuario realmente necesita resolver.

Tener un problema propio no lo convierte automáticamente en una oportunidad de mercado. Lo que sí aporta es una ventaja inicial: uno conoce el momento exacto en que aparece la frustración, los atajos que intenta y el lenguaje con el que la gente lo explica.

En este caso, no hacía falta una enciclopedia de teoría musical. Hacía falta feedback inmediato mientras se practica y una guía breve cuando se toca. Esa diferencia entre “aprender sobre algo” y “necesitar hacer algo” terminó definiendo el producto.

La experiencia propia es el comienzo de la investigación, no su reemplazo. Después hay que preguntar quién más vive esa fricción, cuándo aparece, qué alternativa usa y qué precio paga por no resolverla. Ahí se separa una historia interesante de un problema que merece producto.

Para EscalaImprov, esa observación llevó a separar dos momentos que parecían iguales: Estudio, para entender escalas, acordes e intervalos; y Jam, para tocar con una guía corta, notas de reposo y un click. No era una decisión estética: eran dos trabajos distintos.

Construir algo propio no deja solo una aplicación publicada. Deja una forma de mirar el siguiente problema. En este caso, diseñar una herramienta de estudio obligó a entender de verdad el círculo de quintas, el feedback instantáneo y por qué tocar con mouse es incómodo.

El mismo patrón se repite entre dominios muy distintos. MiCuota dejó una base de pagos auditables; Patio, decisiones de multi-tenancy; WebSpec AI, un flujo para especificar. El activo más interesante no siempre es el producto: a veces es la capacidad reutilizable que quedó detrás.

Principio de producto: una experiencia propia no reemplaza la validación, pero produce mejores hipótesis iniciales y ayuda a separar funcionalidades de trabajos reales del usuario.

Your Product Page Promises 7 Days. AliExpress Standard Takes 15 to 45.

📅 Nov 17, 2026  |  Category: Technology  |  Read Source →

Your product page says delivery in 7 to 10 days — because the template said it, a competitor said it, or it felt like the number that would convert. On day ten the first "where is my order?" message arrives. Tracking shows the parcel moving normally, just not inside the window you promised. The customer is not wrong: the shipping method you used was never going to meet it.

AliExpress Standard Shipping typically takes 15 to 45 days depending on destination, season, and customs. That is not a supplier failure. It is the published reality of the cheapest default lane. Stores get into trouble not because shipping is slow, but because the promise on the page and the lane on the order describe two different businesses.

This post is about closing that gap: which AliExpress shipping lanes actually take how long, how to set a delivery window you can keep, and what to do when the honest window looks too slow to sell.

Sellers often pick a shipping option by price alone at order time, without mapping it to the promise they made at sale time. Here is the working comparison I use when auditing a store's setup, based on current carrier and seller guidance — always confirm against the estimated delivery date shown on the specific product, because supplier processing speed varies:

Estimates often hide processing and customs. Real delivery time is processing (often 1 to 3 days) plus transit plus customs (often 1 to 5 days): a "15-day transit" lane is an 18 to 23 day customer experience. Peak periods stretch everything — Black Friday, December holidays, and Chinese New Year in late January and February, when logistics pauses for one to two weeks or more. US sellers must also update landed-cost math: in May 2025 the US removed the $800 duty-free threshold for imports from China and Hong Kong, so parcels now carry additional duty cost by declared value.

Nobody sets out to mislead buyers. The short window creeps in: themes and import tools ship optimistic defaults nobody edits; sellers copy a competitor who may be making the same mistake; and there is a real fear that an honest window will kill conversion, so support absorbs the difference instead. But most buyers expect delivery within about 7 to 10 business days, so a Standard lane was never going to feel "normal" anyway. Hiding the wait does not shorten it — it only decides whether the customer feels informed or deceived. Sellers who state real times upfront consistently report fewer refund requests, because a buyer who knowingly accepted 18 days rarely disputes on day ten.

Step 1: Fix the lane per product before you write any text. For each product you actually advertise, decide which shipping option you will use at fulfilment — not the cheapest option on the listing, the one you will really pick. If you would never ship an advertised product by Super Economy, remove it from your mental math entirely.

Step 2: Build the window from the full formula. Processing plus realistic transit for your main destination plus a customs buffer — then publish the upper half of that range, not the best case. A plain sentence like "Delivery typically takes 15 to 25 days depending on your location," linked to a shipping page with the per-method table, beats a short number that is wrong. Specific and slightly conservative wins.

Step 3: Put the window where buyers decide. On the product page near the buy button, in checkout if your platform allows it, and in the confirmation email — with the same numbers everywhere. A mismatch between product page and policy page reads as a trap, because it is one.

Step 4: Make tracking reassure. Half of "where is my order" tickets are really "is anything happening?" tickets. Get the tracking number to your store and customer at ship time, and say when to expect first movement. A parcel visibly moving on day three generates a fraction of the tickets of a silent one. If tracking is copied by hand, that step is where this breaks — automate or checklist it before spending on ads.

Step 5: Pre-write delay messages and re-audit on change. Write a proactive delay note, a mid-window reassurance, and a missed-window apology with a remedy — before peak season. And when you switch suppliers, reset the window: a supplier change is a product-page change.

You sell a home accessory for $34.99 with free shipping, fulfilled by AliExpress Standard. Your page promises 7 to 10 days. Reality is 2 days processing plus 15 to 35 days transit plus customs — call it 19 to 40 days door to door. In a typical month you get 100 orders and roughly 25 "where is my order" contacts, 6 refund requests citing delivery time, and 2 chargebacks.

You have three honest options. One: keep Standard, publish "18 to 30 days," and accept a conversion dip. Two: switch to Premium at about $3.50 more per order, publish "8 to 15 days," and raise the price to $37.99 or absorb part of the cost — your break-even ad math tells you how much room you have. Three: source from a supplier with US warehouse stock at higher product cost and publish "3 to 7 days." There is no option four where Standard delivers in a week. Even halving delivery-related refunds just by publishing an honest window — no lane change — is worth more than the conversion it costs, because remaining buyers accepted the wait before paying.

Read your bestseller's page and find the delivery promise. Then open its last real order and check the lane and actual time. If those two numbers disagree, fix the page today — from the lane backwards, processing and customs included — and make sure tracking reaches the customer without a manual step in between. A slower promise you keep builds the reviews and repeat orders that a fast promise you break never will.

How far apart are the window on your product page and the lane you actually ship with? That gap, in days, is the most useful number in this whole post. Tell me yours in the comments.
