PrivaSearch: private AI search with SearXNG and a local LLM

📅 Nov 08, 2026  |  Category: Technology  |  Read Source →

I wanted AI-synthesized search answers without sending my queries to anyone. PrivaSearch is the result: SearXNG for metasearch, a local LLM served by Ollama for cited answers, and a small Node/Express API in between. Here's how it's put together and what it does and doesn't guarantee.

Four containers on one internal Docker network (privanet):

Only the frontend publishes a host port (8080 by default). SearXNG, Ollama and the API have no ports: mapping, so they're unreachable from outside Docker. The only routine outbound traffic is SearXNG querying upstream search engines, which is the fundamental job of a metasearch engine.

The browser first asks GET /api/results for paginated SearXNG results, then calls POST /api/answer with the top N of those results to stream a RAG answer. Splitting them means you can change how many sources the model considers and regenerate the answer without re-querying the web.

The answer handler is short. It takes the caller's sources, builds the prompt, and streams tokens as they arrive from Ollama:

Ollama's /api/chat returns newline-delimited JSON when stream: true, and ollama.js parses it line by line. If the client disconnects, an AbortController cancels the generation.

The system prompt (in prompt.js) constrains the model to the numbered results: write one direct answer in your own words, don't summarize sources one by one, cite each claim with [n], never add outside knowledge, and if the results don't contain enough information, reply with exactly "Insufficient information in the results." Each source is reduced to one line, [index] title — snippet, with no URLs, because the model doesn't need them and echoing them encourages source-by-source listing. The default temperature is 0.2 for factual answers. These prompt builders have unit tests that run in CI.

If the LLM is down or the model isn't pulled, the raw SearXNG results still render with a notice. If there are no results, you get an explicit "no results" message rather than a generated answer.

The API's only runtime dependency is Express. Node's built-in fetch covers HTTP. Even the SOCKS5 client used to discover the Tor exit IP is a small dependency-free module (socks.js, about 60 lines). For a privacy project, fewer dependencies means less attack surface and less to audit.

By default, upstream engines see your real IP. Two optional overrides route SearXNG through a tunnel:

Per the privacy statement in the README: your query lives only in API and SearXNG process memory, search results are held only for the request, and generated answers are streamed to your browser and not stored. What is persisted is the model weights (the ollama-models volume) and the SearXNG config. SearXNG is hardened with query logging off, no Redis attached, autocomplete off (no per-keystroke leakage) and remote images proxied. Thumbnails go through /api/image_proxy, so your browser never contacts remote image hosts, and the API refuses to proxy anything that isn't an image.

Two opt-in features make extra requests, and both can be disabled: Summarize fetches the one page you click (ALLOW_PAGE_FETCH=false turns it off), and the exit-location widget does one cached geo-IP lookup (SHOW_LOCATION=false turns it off). Both are disclosed in the app's privacy panel.

The default model is qwen2.5:1.5b (about 1 GB), chosen for CPU: it loads in seconds and the README reports about 8 s per warm answer. qwen2.5:0.5b is faster but weaker at citations, and llama3.1:8b gives better answers but is slow on CPU. The model is kept resident for 30 minutes (OLLAMA_KEEP_ALIVE) so you only pay the load cost once.

Then open http://localhost:8080. Source: https://github.com/HaidarESBER/privasearch

Making browser perception cheap for LLM agents: snapshots, caching and diffs

📅 Nov 08, 2026  |  Category: Technology  |  Read Source →

Most "give the model a browser" setups hand it one of two things: a screenshot, or a dump of the full accessibility tree. Both are expensive, and both get re-sent in full after every action.

I've been building ecobrowser, a TypeScript library and MCP server on top of Playwright whose whole job is to make perception cheap for a model. This post walks through three pieces of it, using the real code: a compact snapshot format, a cache keyed on the DOM, and a diff for re-perceiving after an action.

A snapshot is not a picture of the page. It's a list of interactive elements:

Each element is stamped with a durable data-ai-id, and the model acts by id (click e3), never by CSS selector or pixel coordinate. The state array carries what the model needs to act correctly, and covered elements are flagged obscured. Password values are never captured and show as [redacted].

The snapshot is capped at 250 elements, and it only covers interactive elements. That's a deliberate scope choice, and it matters for the benchmark below.

Re-walking the DOM and re-serializing on every call is wasteful when nothing changed. The engine runs a MutationObserver that counts real DOM changes (ignoring its own data-ai-id stamping), and snapshot() serves the previous result when the DOM version and URL match:

After a click, the model rarely needs the whole page again. changes() returns only the delta:

The interesting part is how elements are matched between the two snapshots. Ids that appear exactly once in both are matched by id, so a relabelled button shows up as changed rather than as one removal plus one addition. Everything else is matched by a semantic signature (tag|role|name) plus an occurrence index, so five identical buttons are matched positionally instead of collapsing into one key. A toggled checkbox counts as changed because the comparison includes value and the state flags, not just the label.

For "just give me the search box", there's a deterministic scorer, elementMatchScore. Words like box, field, button and link are treated as kind hints and matched against tag and role. The remaining words are scored against the accessible name: exact beats prefix beats substring beats all-words-present. A kind match boosts the score and a kind mismatch demotes it, so "search box" ranks the search input above a "Search" button. It's cheap precisely because no model is involved.

The caveats matter, and they're in the README too:

It's a young, single-user developer tool, tested on its own paths (34 unit tests, 21 browser regression tests and 7 MCP-level regression tests, all run in CI) but not battle-hardened across thousands of real sites. It's meant to be pointed at your own or authorized sites.

British Airways Boeing 787 Stranded In Pittsburgh For 2 Months Due To Complicated Repairs

📅 Nov 08, 2026  |  Category: Other  |  Read Source →

A British AirwaysBoeing 787-8 Dreamliner has been stranded at Pittsburgh International Airport (PIT) in Pennsylvania for over two months after reportedly sustaining significant damage during a ground-handling incident. The aircraft, registered as G-ZBJF, arrived at PIT from London Heathrow Airport (LHR) on August 28, 2026, operating as flight BA 171. However, instead of a routine transatlantic arrival, a ground service vehicle collided with the aircraft, damaging its underside and rendering it unable to return to the skies ever since.

More than 70 days later, the 12-year-old Dreamliner remains in Pittsburgh, with reports flagged by Turbine Traveller suggesting that the repair process has proven to be much more complicated than initially anticipated. As reported by several travelers, potential damage to the aircraft’s landing gear system continues to delay the maintenance repair process. Simple Flying has reached out to British Airways for comment on G-ZBJF’s extended stay in the City of Bridges and will update coverage upon receiving a response.

G-ZBJF arrived in Pittsburgh on August 28, 2026, after completing its roughly 3,233-nautical-mile (5,987 km) journey across the Atlantic Ocean. The aircraft had departed Heathrow five minutes early of its 4:40 PM departure time, landing in Pennsylvania at approximately 8:23 PM local time. However, the G-ZBJF never operated its return service to London later that night, with subsequent reports indicating that the 787-8 had sustained severe damage while on the ground. Flight tracking data and visual sightings of the jet confirm that the aircraft is still on the ground in Pittsburgh as of November 8, 2026.

According to discussions among aviation enthusiasts on Reddit, the incident that led to G-ZBJF’s grounding involved a mobile baggage belt loader that reportedly struck the airframe underneath one of its bulk cargo doors. The belt loader, a piece of ground service equipment used by ramp personnel to load and unload luggage from the 787’s cargo hold, was raised up into position but ended up piercing the fuselage, leaving a hole in the cargo bay’s exterior. Although the exact details beyond this have not been confirmed, the continued presence of the aircraft in Pittsburgh suggests a major structural issue requiring a significant engineering solution.

The repair process could be particularly challenging given the Boeing 787’s construction. Unlike older aircraft that primarily use conventional aluminum structures, about 50% of the Dreamliner’s primary structure is made from composite materials. This includes significant portions of its fuselage and wings, requiring specialized inspection and repair procedures in the event of substantial structural damage.

Depending on the severity, British Airways maintenance engineers may have to construct a specialized patch to apply to the exterior of the Dreamliner. This would allow the plane to be ferried to a larger maintenance base capable and equipped to handle the 787 where more extensive work can be completed. In order to be transported to one of these locations, however, the aircraft would have to be approved by the FAA to complete a one-off ferry flight via the use of a FAA special flight permit (SFP).

Since the initial damage to G-ZBJF, several people have reported the aircraft is potentially also facing damage to the landing gear system. According to a commenter on a November 8th discussion thread, a British Airways engineer who had worked on the Dreamliner said repair work was well underway on the aircraft, but technicians had encountered additional complications involving damage to the jet’s landing gear system. While this account has not been independently verified, it could help explain why the Dreamliner has remained grounded for so long.

A separate report suggests that British Airways could be preparing to reposition the airplane to Cincinnati Northern Kentucky International Airport after completing temporary repairs in Pittsburgh. The reported plan would potentially allow the 787 to be moved to a larger facility operated by FEAM Aero, a maintenance services provider, where the aircraft could be more permanently repaired before returning to the United Kingdom. Ferrying the jet to Boeing’s 787 facilities in Seattle could also be another option, as Boeing would be well-equipped to handle any repairs to the aircraft’s composite structure if needed.

For British Airways, getting G-ZBJF back into the skies is a high priority. Currently, the UK flag carrier operates a total of 12 Boeing 787-8 aircraft according to planespotters.net. G-ZBJF is approximately 12 years old, having first flown in April 2014 before being delivered to British Airways the following month. While it is not uncommon for airplanes to be parked for routine maintenance checks, the prolonged grounding of G-ZBJF is costing the airline not only potentially millions in repair fees, but hundreds of thousands in lost revenue potential and roughly $175,000 in gate parking charges, according to the rates published by the Allegheny County Airport Authority which runs Pittsburgh International. While British Airways likely isn’t paying this full amount given insurance coverage and the fault of the ground service operator, it goes without a doubt the airline would rather have its aircraft flying passengers than sitting on the ground in Pittsburgh.

The incident delayed the flight's departure by several hours.

Interestingly, the Pittsburgh incident is not the first time this year G-ZBJF has spent an extended period away from flying passengers. Before its latest grounding, the Dreamliner already spent nearly eight months at Cardiff Airport (CWL) in Wales, where British Airways operates a major maintenance facility, being placed into long-term storage before D-checks were completed on the Dreamliner. Aircraft tracking records show that G-ZBJF arrived in Cardiff on December 19, 2025, and remained there until August 6, 2026. After nearly eight months in Cardiff, the aircraft returned to commercial operations on August 7, 2026, meaning it had only been back in service for approximately three weeks before being stranded in Pittsburgh.

G-ZBJF ferried to Cardiff for long-term storage and maintenance checks.

G-ZBJF completes D-check at Cardiff maintenance base.

G-ZBJF returns to operational service after being ferried from Cardiff to London.

G-ZBJF operates BA171 from LHR to PIT and is subsequently grounded in Pittsburgh after a ground service vehicle collided with the aircraft's underside.

The timing makes the latest incident particularly unfortunate for British Airways. Having spent much of the previous eight months undergoing extended maintenance, G-ZBJF had only recently returned to its regular flying schedule before the incident in Pittsburgh. In the meantime, the prolonged grounding underscores the heavy logistical challenges of repairing a widebody thousands of miles away from primary maintenance facilities. Whether the 787 will be able to eventually return to service directly from Pittsburgh or first have to be repositioned to another city remains one of the biggest unanswered questions.

Syndicated reporting provided by Stats Perform and reviewed by the SoccerNews editorial team.

Michael Carrick expects to still be in charge of Manchester United after the international break, despite the Red Devils sitting in the Premier League's relegation zone.

United will spend the upcoming hiatus 18th in the table, despite launching two stirring fightbacks to take a point from a chaotic 4-4 draw with Aston Villa on Sunday.

The Red Devils trailed 2-0 after just three minutes and 40 seconds – the earliest they have ever trailed by multiple goals in a Premier League game – before roaring back to go into half-time at 2-2.

Villa then hit another quickfire double in the first eight minutes of the second half to again leave United up against it, and they still trailed 4-2 going into the second minute of second-half stoppage time.

However, Patrick Dorgu teed up Joshua Zirkzee to cut the deficit, then headed Bruno Fernandes' 96th-minute corner home to salvage the unlikeliest of points for Carrick's team.

But even with United becoming the first team in Premier League history to fight back from two goals down to equalise on two occasions in a single game, Carrick's future was still a hot topic after full-time.

United had been tipped to make a change in the dugout during the international break, having gone eight league games without a victory for just the second time, previously enduring such a run in April and May 2025 under Ruben Amorim.

Before facing Liverpool on November 22, United are guaranteed to spend at least 15 consecutive days in the relegation zone, marking their longest run of days in the drop zone since a 28-day period in September and October 1986.

But when asked if he could step away from the Old Trafford hot seat, Carrick told Sky Sports: "It's not going to happen, no."

That was part of a tense exchange with interviewer Patrick Davison, who suggested to Carrick that a change in management was thought to be a possibility.

Carrick replied: "Is there? We understand the situation; we haven't won enough games.

"But I expect to move forward and keep working on things we've been working on. We showed a lot of good in the game.

"If we tighten up on a few mistakes, we will win football matches."
