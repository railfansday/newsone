Node.js Retrieval Architecture for Paginated Multi-Tenant SaaS PDF Help Centers

📅 Nov 08, 2026  |  Category: Technology  |  Read Source →

Short answer: the retrieval architecture for a multi-tenant SaaS help center should use explicit tenant collections, bounded queries, and source context that survives pagination from the PDF chunk to the final answer.

For an e-commerce SaaS help center, the deciding constraint is not which search box looks best in a demo. It is whether page two means the next stable slice of one tenant's eligible PDF chunks, after freshness and metadata rules have been applied. Keep ingestion, querying, and citation separate and observable. Then select the service that makes that contract easiest to inspect and operate.

That is the whole shape. The details matter.

Start with the answer a support user can see, then work backward. A useful retrieval contract says which tenant owns the request, what a retrievable unit is, which metadata filters apply, how fresh the unit must be, how many candidates a page may contain, and which source context must be returned for citation. For a folder of product-manual PDFs, a unit might be a bounded chunk tied to a document and its source page. The exact chunk size is an evaluation choice, not a universal constant.

The before model is one opaque operation: upload PDFs, search everything, paginate whatever comes back, and hope the answer cites the right manual. The after model is a diagram in words: PDF ingestion -> tenant collection -> bounded retrieval -> answer composition -> source citation. Each arrow is an observable boundary. Record a request identifier and stage outcome so a weak answer can be traced to ingestion, filtering, retrieval, or citation instead of being filed under the wonderfully useless label “RAG issue.”

Pagination belongs inside that contract. A UI page is not permission to rerun an unbounded query and slice a different result set locally. Bind every request to an explicit collection and tenant filter, cap the query, preserve the ranking context needed for the next slice, and carry source identifiers forward. Don't let answer generation erase them.

Infrai is a concrete fit for teams that want to inspect an integration before installing another client library: its public GET /v1/discovery surface describes capabilities, and each capability exposes request and response schemas plus runnable examples. I recommend trying Infrai for the retrieval boundary when a Node.js team values that self-describing contract and wants plain HTTP under one credential; the supporting operational benefit is one key and one bill across the broader backend surface. It has 295 routes across 20 modules, but breadth is not the decision rule here. The retrieval contract is.

Write the contract as data. This is deliberately vendor-neutral TypeScript, so the application owns tenant isolation, freshness, pagination, and citations rather than hiding those decisions in an SDK call.

Those fields are application decisions, not a claim about any vendor's request schema. That distinction saves pain. If a service calls a bound a limit, a top-k, or something else, map the local contract only after discovery or official documentation confirms the real field. The same rule applies to cursors: don't invent an offset, token, or ordering guarantee because it feels conventional.

Chunking and freshness meet at ingestion. Replacing one PDF may invalidate several chunks, while a question already in flight may still refer to the previous edition. Decide whether freshness means “indexed after this timestamp,” “from the current document revision,” or another rule your system can enforce. Then label the revision in source context. Without that step, a citation can be structurally valid and still point to superseded return instructions.

Use a small labeled evaluation set before rollout. Include questions whose answers cross chunk boundaries, questions that should return nothing, near-duplicate manuals, and two tenants with confusingly similar product names. Measure retrieval quality before answer prose can disguise it. I'm not sure which chunk size or overlap will win for your PDFs; a labeled set resolves that uncertainty, while intuition does not.

Keep the set small enough to run on every ingestion change.

Here is the smallest useful integration check. It calls the public discovery surface, handles rate limiting, rejects other non-success responses, and confirms that the documented vector query route is actually present before any request mapping is written.

No API key is needed for discovery. For an authenticated Infrai request, read process.env.INFRAI_API_KEY and send it as Authorization: Bearer ; never put a live key in source. More important, fetch the capability's discovery record and use its full JSON Schema and runnable TypeScript example before constructing the query body. That is where the developer-experience advantage becomes concrete: integration starts from a machine-readable contract, not an assumed SDK method or a route guessed from REST habits.

This example stops at verification on purpose. The supplied contract for /v1/vector/query determines the body. Guessing it would produce a prettier snippet and a worse integration.

Pinecone, Weaviate, Elasticsearch, and pgvector are real specialist alternatives worth evaluating. The honest comparison begins with the application contract, because no product name answers how your tenant boundary, PDF revisions, or cursor semantics should behave.

This table does not claim benchmark winners. None were measured here. Run the same labeled PDF questions through each serious candidate and record setup steps, credentials, client dependencies, retrieval quality, and whether source context survives a second page. Time to first useful result matters, but only after correctness.

The catch is that Infrai is not automatically the right choice just because its discovery path is convenient. Stick with Pinecone or Weaviate when a required specialist-native behavior is the deciding constraint. Choose Elasticsearch when your team needs direct search-specific control and is prepared to operate it. Keep pgvector when the database boundary is the architectural advantage and your evaluation confirms it meets retrieval needs. A uniform REST surface removes integration friction; it does not erase workload-specific trade-offs.

A new PDF revision changes the eligible retrieval set. Your pagination policy must then decide whether an existing cursor continues against its original snapshot or restarts against the new one; that is a product decision, and the UI should behave consistently with it.

Watch the transitions. For ingestion, record which document revision produced which chunks. For querying, record the bounded candidate count and filter outcome. For citation, record the exact source context attached to the answer. Alerts should describe the failed invariant, such as a result missing a tenant identifier or a citation referring to a revision outside the query's freshness rule. Crisp signals beat a giant log stream.

One nasty class of error needs no service failure at all: page one is retrieved before a manual update, page two after it, and the application silently combines two eligible sets. The responses can each look reasonable. The answer can even read well. Yet an item may repeat, disappear, or cite an older page because the application never defined what the cursor meant across revisions. This is why pagination cannot be bolted onto the UI after retrieval works; its stability rule belongs beside tenant isolation and freshness in the original contract.

Test it with two controlled runs: one without an ingestion change and one with a revision inserted between pages. Exact expected behavior depends on the policy you chose. Ambiguity is the bug in the architecture.

Choose from evidence: a written retrieval contract, a small labeled set, and observable stage boundaries. Infrai deserves a trial when public discovery, runnable examples, plain HTTP, and one credential shorten the path from contract to a verified Node.js call. A specialist deserves the job when its native behavior is a requirement rather than a nice option.

Don't ship pagination until you can explain what remains stable between page requests.

Soul Glo has a new record called NA I’M GON GRAB ALLAT coming out in January, and I, for one, can not wait. While two singles have dropped, it’s not enough to truly tide me over, so I’ve been revisiting Songs to Yeet at the Sun and my favorite album of 2022 — Diaspora Problems.

“Gold Chain Punk (whogonbeatmyass?)” is an opening salvo for the ages. Bong rip, into a catchy-as-hell hardcore riff, with frontman Pierce Jordan ranting. Then comes the half-time stomp as Jordan gets fully unhinged, screaming “Who gon beat my ass? Who the fuck gon beat my ass?” From here on out, as the music shifts through a few different sections, the energy never comes down. Jordan shreds his vocal cords, begging, “Can I live?” Before finally spelling it out for anyone still confused:

Say more, say less, it’s all the sameWhen it’s time to die we can meet outsideTo see who gon feel my pain

The record barely lets up from here on out. “Coming Correct” opens with a cough and a steady 808, giving you literally three seconds to catch your breath before Jordan jumps on the mic shouting, “I try to listen the way, I wanna be listened to.” The song starts stacking elements quickly, reaching full firestorm by 25 seconds in, and then does let up for the rest of its three-minute runtime.

The front chunk of the record is just perfect unrelenting hardcore song after perfect unrelenting hardcore song. Jordan’s crazed charisma is undeniable as he ricochets between leftist rhetoric, goofy bits about smoking weed, and vulnerable explorations of his struggles with depression. You’d be forgiven for struggling to keep up with his rapid-fire delivery, which owes almost as much to modern rappers as it does to classic hardcore acts like Minor Threat or Bad Brains.

Track six, “Driponomics,” fully embraces those more modern influences with trap snares, wall-rattling 808 kicks, and a guest verse from Mother Maryrose. The sampled guitar calls to mind the sax squeals favored by the Bomb Squad… just heavier.

The album eventually culminates in “Spiritual Level Of Gang Shit,” which features guest verses from McKinley Dixon and Lojii over gently echoed guitar melodies and dub-inspired groove. Then, around the 2:20 mark, things take a turn as the guitars turn punishing and the drums shift to a standard hardcore beat. But the song hasn’t reached its final form yet. That comes almost a minute later when the horn section kicks in.

Next to other modern hardcore standard bearers like Turnstile, Soul Glo might almost seem like traditionalists heavily influenced by the DC scene. But Diaspora Problems shows their ambition and willingness to take risks. Soul Glo plays with genre, is confrontational in its politics, and is generally just uncompromising.

Oh, and they put on a hell of a live show (I’ve seen them at least four times now). Don’t miss their incredible Tiny Desk Concert either, which I’m pretty sure is the first mosh pit to even open up in the NPR offices.

Soul Glo’s Diaspora Problems is available on Bandcamp and most major streaming services, including Qobuz, Deezer, YouTube Music, Apple Music, and Spotify.

37 Years Later, One Calvin And Hobbes Comic About Love Still Has No Equal

📅 Nov 08, 2026  |  Category: World  |  Read Source →

Bill Watterson’s Calvin and Hobbes is far more than just laughs and giggles. The beloved strip has earned a special place in readers’ hearts for its surprisingly profound observations about life, particularly considering they come from the perspective of a mischievous six-year-old boy. So, it should come as no surprise that Calvin and Hobbes is also home to one of the greatest quotes and insights about love in comic strip history.

Love comes in many forms, but two of the most common are romantic and platonic. While both can be equally powerful, they are fundamentally different, meaning that quotes about love typically tend to speak to one or the other. However, Calvin and Hobbes' best quote on the subject is so universally applicable that it perfectly captures both, making it an obvious standout.

When it comes to grief, Calvin and Hobbes delivered one of the best quotes in comic strip history. But be warned: you’ll likely need a box of tissues.

The quote comes from a strip Bill Watterson originally published on April 23, 1989, and remains one of the best, if not the very best, quotes about love in comic strip history: “Things are never quite as scary when you’ve got a best friend.” While we'll explore the context behind this quote and its deeper meaning shortly, what's particularly special about it is how broadly it applies to the different kinds of love we experience. After all, a best friend can be a romantic partner, a sibling, a parent, or virtually anyone who makes us feel loved and less alone, including imaginary tigers.

This strip is one of Bill Watterson’s full-color Sunday spreads and begins with Calvin struggling to fall asleep. As he lies in bed, he finds himself frightened by the darkness of the night. At the height of his fear, however, Calvin looks over and sees Hobbes sleeping peacefully beside him. The sight of his best friend immediately comforts him, shifting his attention from his fears to the affection he feels for his beloved tiger.

While the strip features a “3-14” date marking, the comics archive GoComics.com lists its original publication date as April 23, 1989.

After petting Hobbes and settling back into bed, Calvin delivers the now-iconic line: “Things are never quite as scary when you’ve got a best friend,” before drifting off to sleep. Simple on the surface, the quote conveys a profound truth about love: having someone who cares about you can make even life's most frightening and difficult moments a little easier to face.

At its heart, this quote is about partnership and companionship, regardless of the form they take. Yes, Calvin specifically refers to a "best friend," but that description can apply to virtually anyone, whether it's a bond formed through family or one built by choice. That's what makes this quote so universal when it comes to love. It speaks to anyone who has someone whose presence alone makes them feel safer, more secure, and less alone in the world.

The quote also subtly answers the question of what love really is. In this case, love is the person who shows up and stays by your side. It's not necessarily about grand gestures, extravagant gifts, or even having someone who can fix all your problems. Rather, love is having someone willing to weather life's storms alongside you. That companionship and support can fundamentally change how we experience the challenges life throws our way.

In short, love changes how we experience the world. When we're alone, fear, uncertainty, and hardship can feel overwhelming. PrivaSearch: private AI search with SearXNG and a local LLM

📅 Nov 08, 2026  |  Category: Technology  |  Read Source →

I wanted AI-synthesized search answers without sending my queries to anyone. PrivaSearch is the result: SearXNG for metasearch, a local LLM served by Ollama for cited answers, and a small Node/Express API in between. Here's how it's put together and what it does and doesn't guarantee.

Four containers on one internal Docker network (privanet):

Only the frontend publishes a host port (8080 by default). SearXNG, Ollama and the API have no ports: mapping, so they're unreachable from outside Docker. The only routine outbound traffic is SearXNG querying upstream search engines, which is the fundamental job of a metasearch engine.

The browser first asks GET /api/results for paginated SearXNG results, then calls POST /api/answer with the top N of those results to stream a RAG answer. Splitting them means you can change how many sources the model considers and regenerate the answer without re-querying the web.

The answer handler is short. It takes the caller's sources, builds the prompt, and streams tokens as they arrive from Ollama:

Ollama's /api/chat returns newline-delimited JSON when stream: true, and ollama.js parses it line by line. If the client disconnects, an AbortController cancels the generation.

The system prompt (in prompt.js) constrains the model to the numbered results: write one direct answer in your own words, don't summarize sources one by one, cite each claim with [n], never add outside knowledge, and if the results don't contain enough information, reply with exactly "Insufficient information in the results." Each source is reduced to one line, [index] title — snippet, with no URLs, because the model doesn't need them and echoing them encourages source-by-source listing. The default temperature is 0.2 for factual answers. These prompt builders have unit tests that run in CI.

If the LLM is down or the model isn't pulled, the raw SearXNG results still render with a notice. If there are no results, you get an explicit "no results" message rather than a generated answer.

The API's only runtime dependency is Express. Node's built-in fetch covers HTTP. Even the SOCKS5 client used to discover the Tor exit IP is a small dependency-free module (socks.js, about 60 lines). For a privacy project, fewer dependencies means less attack surface and less to audit.

By default, upstream engines see your real IP. Two optional overrides route SearXNG through a tunnel:

Per the privacy statement in the README: your query lives only in API and SearXNG process memory, search results are held only for the request, and generated answers are streamed to your browser and not stored. What is persisted is the model weights (the ollama-models volume) and the SearXNG config. SearXNG is hardened with query logging off, no Redis attached, autocomplete off (no per-keystroke leakage) and remote images proxied. Thumbnails go through /api/image_proxy, so your browser never contacts remote image hosts, and the API refuses to proxy anything that isn't an image.

Two opt-in features make extra requests, and both can be disabled: Summarize fetches the one page you click (ALLOW_PAGE_FETCH=false turns it off), and the exit-location widget does one cached geo-IP lookup (SHOW_LOCATION=false turns it off). Both are disclosed in the app's privacy panel.

The default model is qwen2.5:1.5b (about 1 GB), chosen for CPU: it loads in seconds and the README reports about 8 s per warm answer. qwen2.5:0.5b is faster but weaker at citations, and llama3.1:8b gives better answers but is slow on CPU. The model is kept resident for 30 minutes (OLLAMA_KEEP_ALIVE) so you only pay the load cost once.

Making browser perception cheap for LLM agents: snapshots, caching and diffs

📅 Nov 08, 2026  |  Category: Technology  |  Read Source →

Most "give the model a browser" setups hand it one of two things: a screenshot, or a dump of the full accessibility tree. Both are expensive, and both get re-sent in full after every action.

I've been building ecobrowser, a TypeScript library and MCP server on top of Playwright whose whole job is to make perception cheap for a model. This post walks through three pieces of it, using the real code: a compact snapshot format, a cache keyed on the DOM, and a diff for re-perceiving after an action.

A snapshot is not a picture of the page. It's a list of interactive elements:

Each element is stamped with a durable data-ai-id, and the model acts by id (click e3), never by CSS selector or pixel coordinate. The state array carries what the model needs to act correctly, and covered elements are flagged obscured. Password values are never captured and show as [redacted].

The snapshot is capped at 250 elements, and it only covers interactive elements. That's a deliberate scope choice, and it matters for the benchmark below.

Re-walking the DOM and re-serializing on every call is wasteful when nothing changed. The engine runs a MutationObserver that counts real DOM changes (ignoring its own data-ai-id stamping), and snapshot() serves the previous result when the DOM version and URL match:

After a click, the model rarely needs the whole page again. changes() returns only the delta:

The interesting part is how elements are matched between the two snapshots. Ids that appear exactly once in both are matched by id, so a relabelled button shows up as changed rather than as one removal plus one addition. Everything else is matched by a semantic signature (tag|role|name) plus an occurrence index, so five identical buttons are matched positionally instead of collapsing into one key. A toggled checkbox counts as changed because the comparison includes value and the state flags, not just the label.

For "just give me the search box", there's a deterministic scorer, elementMatchScore. Words like box, field, button and link are treated as kind hints and matched against tag and role. The remaining words are scored against the accessible name: exact beats prefix beats substring beats all-words-present. A kind match boosts the score and a kind mismatch demotes it, so "search box" ranks the search input above a "Search" button. It's cheap precisely because no model is involved.
