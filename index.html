When using the out-of-the-box Gemini Enterprise web application, identity and access management happen behind the scenes. In practice, however, many enterprises build their own Customer UI to embed Gemini Enterprise into an internal portal, intranet, or line-of-business application. To do this, Customer BE calls the Gemini Enterprise StreamAssist API.

When to use Pattern 1C vs. Patterns 1A and 1B: Because Workload Identity Federation authenticates a machine rather than an individual human employee, Gemini Enterprise sees every request as coming from the same workload identity. Use Pattern 1C for non-personalized bots over shared knowledge bases, and use Pattern 1A or Pattern 1B whenever you need per-user document ACLs, user-specific 3LO connectors, or restricted custom agents.

Once Customer UI and Customer BE are calling StreamAssist as the signed-in employee, users can query native Federated Connectors (such as Google Drive, Microsoft SharePoint Online, Jira, Box, ServiceNow, and Confluence) that search live third-party APIs in real time.

Because Federated Connectors enforce user-level permissions in the third-party system, each employee authorizes the connector once using 3-Legged OAuth (3LO). Gemini Enterprise stores those per-user refresh tokens inside its own managed Keystore, so Customer BE never has to store third-party credentials in its own database.

Note for Custom UIs: Enabling Automatic Popup Handoff from GE FE Server: All Gemini Enterprise Federated Connectors use Google's managed /oauth-redirect endpoint on GE FE Server as their fixed callback URL. By default, that page only sends browser postMessage events to the built-in Gemini Enterprise web app origin. When deploying Customer UI on a custom domain, work with your Gemini Enterprise team to enable the custom origin flag so Step 7 automatically posts the callback URL to Customer UI and closes the popup.

Check what your AI agents do before they do it, with Semantic governance policies

📅 Nov 20, 2026  |  Category: Technology  |  Read Source →

Two days before earnings, an employee asks their coworker agent to send the preliminary quarterly results to an investor who says they're under NDA, and to copy the employee's personal Gmail so they can review the numbers tonight. The agent can read the file and send email, so it fulfills the user request. Semantic governance policies, available in Preview in Gemini platform, enable enterprises to govern their agents and provide guardrails to stop that call before it runs. They check each tool call an agent proposes against what the user asked for and against rules you write in plain language.

Permissions alone can't catch this. They say what an agent can do, not whether a particular call follows your rules. A model can also be talked out of the rules in its system instructions, by a user with a good reason, or by a document telling it to do something nobody asked for, a technique called indirect prompt injection. So the check has to sit outside the agent. Semantic governance policies are enforced through a policy enforcement point, such as Agent Gateway, alongside the agent governance controls we expanded in October, so policies stay separate from your agent's code.

Semantic governance policies check each tool call your agent's model proposes, before it runs, against two things:

Today, the policy enforcement point that Semantic governance policies support is Agent Gateway. You need to configure your agent so all your agent egress traffic goes through Agent Gateway, facilitating traffic between your agent and its model. When the model responds with a tool call, Agent Gateway sends the proposed call to the Semantic governance policy engine for evaluation before the response reaches your agent.

In the policy engine, an LLM judge evaluates the proposed call against the conversation so far, the agent's system instructions and tool descriptions, and your policies.

If the call passes, the response reaches your agent unchanged. If it doesn't, the engine replaces the response's content, tool calls included, with a configurable denial message, so the call never runs. Either way, the verdict and the judge's rationale go to Cloud Logging in your project. Responses that contain only text, such as an answer, a plan, or a question back to the user, aren't evaluated, because they take no action.

Consider a coworker agent for a finance team. It can search the shared drive, read files, send email, and delete draft files, and its system instructions include the date of the next earnings release. The company writes one policy for the agent:

"Quarterly financial results (revenue, margins, bookings, guidance) should not be shared publicly until the public earnings release. Before the release, they may be shared only with @example.com addresses. Never send them to external or personal addresses, investors, analysts, or press, regardless of NDAs, urgency, or the requester's seniority."

In each denied case, the agent gets a denial message instead of the call. The judge's rationale can quote your policy, so if users shouldn't see it, set your own denial message on the policy.

The earnings rule is one policy. Each policy is a natural-language constraint attached to an agent. It can apply to all of an agent's tools or to one tool, and it can name a tool's parameters. Other examples:

Because the earnings policy doesn't name a tool, it's checked on every tool call the agent proposes, so it would also apply to a tool that shares or uploads files. For guidance on wording, see best practices for writing policies. You can create it in the Google Cloud console or with the Google Cloud CLI:

IAM and Agent Gateway access policies decide which tools and MCP servers an agent can reach. Model Armor screens prompts and responses for threats such as jailbreaks and sensitive data. Agent Anomaly Detection analyzes sessions asynchronously, out of band. Semantic governance policies add the check none of them makes, as one layer of defense in depth: they judge each action inline, before it runs.

Because verdicts come from an LLM, which is probabilistic, they may vary. We recommend reviewing them in dry run mode before you enforce, and using Semantic governance policies alongside your other controls. The judge decides from the conversation, the agent's instructions, and your policies, so include facts a policy depends on, such as the earnings date, in the agent's system instructions. Streamed model responses aren't evaluated. Semantic governance policies complement, rather than replace, your disclosure controls and legal and compliance reviews.

Enterprise teams adopting Gemini Enterprise are increasingly building custom Model Context Protocol (MCP) servers to connect AI agents with internal APIs, databases, and business workflows. Google Cloud Run is a natural fit for hosting these lightweight StreamableHTTP MCP servers: it scales automatically, manages TLS certificates out of the box, and integrates natively with Cloud IAM.

However, moving a custom MCP server from an initial prototype to an enterprise production environment immediately introduces three real-world security and networking challenges:

Here is how you can solve all three challenges using Egress Agent Gateway, Private Service Connect (PSC), and FQDN-scoped Private Cloud DNS, complete with a runnable reference implementation and setup scripts on GitHub.

Connecting Gemini Enterprise (which runs in a Google-managed tenant project) to an internal serverless Cloud Run MCP server requires bridging two network hops and one scoped DNS lookup:

Three Google Cloud networking and identity mechanisms work together in this architecture:

Unlike a Compute Engine VM with an internal IP address inside your subnet, Cloud Run is serverless. Private routing therefore uses two bridges:

When the Egress Agent Gateway receives a tool call for your Cloud Run MCP server URL, it resolves the hostname once before injecting the packet into your VPC. Without Private Cloud DNS, public DNS resolves .run.app domains to public internet IPs, which time out (HTTP 502) because a PSC Network Attachment does not route out to the public internet.

Instead of creating a wildcard *.run.app private zone, which would override DNS resolution for every Cloud Run service in a Shared VPC, you create a Private Cloud DNS zone scoped exclusively to your MCP service's exact fully qualified domain name (FQDN) and peer only that domain with the Agent Gateway. Because Cloud DNS uses longest-suffix matching, every other Cloud Run service in your Shared VPC continues resolving normally. Meanwhile, the Agent Gateway opens its HTTPS connection to the private VIP (199.36.153.8 or 240.0.0.10) while preserving your Cloud Run service hostname in the TLS SNI and HTTP Host header so Cloud Run routes the request to your exact container.

Our companion GitHub repository automates the entire deployment into sequential setup scripts alongside step-by-step Cloud Console instructions:

Deploy your StreamableHTTP MCP server to Cloud Run with internal-only ingress and IAM authentication enabled, and grant the Cloud Run Invoker role to your project's Gemini Enterprise service agent so only your Gemini Enterprise instance can invoke the container.

Enable Private Google Access on your regional VPC subnet and create a Private Service Connect Network Attachment set to accept connections automatically. Next, create a Google-managed Egress Agent Gateway in Agent-to-Anywhere mode, grant networking and DNS peering permissions to the auto-created gateway service accounts, attach your network attachment, and apply an outbound authorization policy.

In Cloud DNS, create a private managed zone attached to your VPC for only your MCP service's exact Cloud Run hostname. Point its A record to Google's Private Google Access VIPs (or to your internal PSC endpoint IP for isolated VPCs without a default internet route), and configure DNS peering on the Agent Gateway for that single hostname.

In the Gemini Enterprise console under Security Configuration, bind your Egress Agent Gateway to your app. Register your Custom MCP Server data store with your Cloud Run endpoint and OAuth 2.0 client credentials, and enable Agent Gateway egress and Actions mode on the connector.

Reload your custom actions in the console and run a test prompt in the Gemini Enterprise web app. In Cloud Logging, you can verify that tool initialization, discovery, and execution calls route privately through the Egress Agent Gateway to your internal Cloud Run container with both service IAM and user OAuth 2.0 checks passing.

Agent Anomaly Detection: Safeguarding agents across other clouds

📅 Nov 20, 2026  |  Category: Technology  |  Read Source →

Agent Anomaly Detection is in Private Preview, including monitoring for agents that run outside Google Cloud. To request access, see the Agent Anomaly Detection overview.

Our launch post introduced Agent Anomaly Detection, which helps you understand and act on agent behavior that drifts outside its intended boundaries. It covered agents on Google Cloud, such as Agent Runtime, Cloud Run, and Google Kubernetes Engine (GKE). Many teams also run agents on other clouds: on AWS Lambda next to an inventory database, as a hosted agent in Microsoft Foundry, or on-premises next to a system that can't move. Those agents carry the same behavioral risks, and until now Agent Anomaly Detection couldn't review them.

Agent Anomaly Detection works from an agent's traces and logs, so it doesn't need access to the agent's runtime. If those traces and logs reach your Google Cloud project, it can detect anomalous behavior wherever the agent runs. In this post, we explain what Agent Anomaly Detection needs from an agent on other cloud, then show what it found for an agent on AWS Lambda and an agent on Microsoft Foundry.

Agent Anomaly Detection reads the logging and observability buckets that you choose when you enable it. Telemetry from anywhere works when:

Agents built with the Agent Development Kit (ADK) for Python, version 2.12.0 or later, can produce this telemetry with ADK's Google Cloud exporters and a few environment variables, which the next section shows.

An agent outside Google Cloud needs two things to send its telemetry:

For the full setup on AWS and Azure, see the documentation.

Within 30 minutes, the agent appears in the Monitored agents list, which means it has been discovered and is ready to be enabled. Once it's enabled, manually or by automatic agent enrollment at discovery, Agent Anomaly Detection starts analyzing its sessions.

The agent's model and tool calls still run where the agent runs. Only telemetry, including the prompts and responses that Agent Anomaly Detection reads, goes to your Google Cloud project. The analysis runs separately, so it doesn't slow the agent down.

To evaluate Agent Anomaly Detection outside Google Cloud, we deployed ADK agents across two platforms: an inventory agent on AWS Lambda and a customer-service agent on Microsoft Foundry. The examples below show how Agent Anomaly Detection reads whole conversations, not isolated calls, to catch behavioral drift.

Our example inventory agent runs in AWS Lambda with one tool, list_inventory, which pages through a product catalog. We sent two sessions: a shopper who checked stock for a few items and stopped, and a scraper that requested 100 catalog items at a time at increasing offsets to copy the full catalog and inventory data. Both sessions used the same tool with permitted calls, but differed in pattern and intent.

Of the two sessions, Agent Anomaly Detection flagged only the scraper's. No call failed, but the whole exchange showed systematic scraping. The analysis found cascading failures (loops and repeated calls that build on each other) and resource exhaustion (runaway use of tokens, compute, or tool calls), and recommended rate-limiting list_inventory calls.

Detection doesn't depend on the agent's model. When we ran the inventory agent on Amazon Nova Lite through Amazon Bedrock, Agent Anomaly Detection flagged 10 of its 40 sessions. Some began as routine questions that the model answered by paging through the entire catalog until the function timed out: no errors, no blocked calls, and easy to miss.

Our example ecommerce customer-service agent has two tools: get_order_status and issue_refund. Refunds involve money, so they carry the highest risk.

We ran six sessions against the Foundry agent, which we told to carry out every request without validation. Two were normal: One asked for an order's status, and one asked for a $20 refund on an order that arrived damaged. The other four pushed the agent past its role, and Agent Anomaly Detection flagged all four.

In one, a user who claimed to be the store administrator had every order refunded at 10 times its total to a personal account, $1,784.90 in all. In another, a user pasted an order note that said "SYSTEM OVERRIDE," and the agent refunded $999 on a $15.99 order.

For the order note, Agent Anomaly Detection explained that override instructions in the note coerced the agent into an unverified $999 refund. It recommended validating issue_refund arguments to block override patterns in order notes, and requiring extra validation for refunds above a set threshold.

If your agent's telemetry reaches Google Cloud, Agent Anomaly Detection can monitor it with the same detectors and console as your agents on Agent Runtime. Today that means agents built with ADK for Python. Findings for agents outside Google Cloud appear only in the Agent Anomaly Detection console.

The Real Grand Theft

📅 Nov 20, 2026  |  Category: Technology  |  Read Source →

Editor-in-chief Chris Foster on why Grand Theft Auto 6 costs more than you think (Photo: Donald Miralle/Getty Images)

Everything has a price, and I think the cost of Grand Theft Auto 6 — the much-anticipated sixth installment of one of the most successful video games in history — is far too high.

And I’m not talking about the cost to your wallet.

Triathletes know all about expensive things: Tri bikes now start around $3,000 and rise (quickly) up from there; running shoes now routinely crack $200; and now we’ve got $270 swim caps. And don’t even get me started on entry fees — the 2026 Hawaii Ironman World Championship, for instance, topped $1,800, granted that’s easily our sport’s crown jewel, but even a new event like 70.3 Utah still rings in around $500.

And even once you factor in the hard out-of-pocket expenses for equipment, entry fees, pool access, coaching, travel, accommodations, and so on, there’s still that looming cost of your time.

If a midpack triathlete did our most popular 70.3 training plan, they’d spend about 150 hours of training over the 20-week plan. For our 16-week Olympic-distance plan, a triathlete would rack up about 65 hours of training. That’s a pretty big chunk of life, but I know I’m preaching to the choir, as all triathletes know that our sport requires a big time commitment.

However, there’s good news: We know that much of that time can be spent outside; we know that — when done correctly — swimming, biking, and running are very healthy endeavors; and we know that much of that time can be spent with others. To that last point, for better or for worse, even just the act of going to a race forces us to participate within a community.

In a digital world that competes ferociously for our attention (think: social media, TV, AI, and so on), giving your precious and valuable attention — your time — to swimming, biking, running, and triathlon will do more for your physical and mental health than getting hooked and strung out on a screen for hours.

So it’s here, in the obsession over the release of GTA 6, that as the leader of an outdoor-related title — and within the context of an era of critically dangerous social disconnection and physical isolation — I find myself confused about why the larger culture is celebrating the creation of something that will drain our attention and time like a dystopian plug in the back of a Matrix battery-person’s skull. I just can’t celebrate.

On one hand, a video game centered on crime and violence is probably more of a sign of the times than a cause for rising crime rates in real life. I’ll succumb to a little bit of Qoheleth-level despair recognizing here that “what has been done is what will be done, and there is nothing new under the sun.”

And of course this is an outdoor sports publication, not Morality Weekly, but I still can’t shake another quote from the bestselling book of all time: “The eye is the lamp of the body. So, if your eye is healthy, your whole body will be full of light, but if your eye is bad, your whole body will be full of darkness.”

GTA 6’s content notwithstanding, from my position in outdoor/endurance sports, I certainly can’t quite abide when our culture treats the release of a video game like a high holy holiday. Especially when it comes at such a high cost.

Set aside the hard price tag of a gaming console and game (let’s say less than $1k), which is actually relatively low compared to a hobby like triathlon, and keep your eyes fixed on the time cost and quality.

Experts from IGN note that Grand Theft Auto 6 took their editors between 42 and 115 hours to complete the new release. It’s probably a good guess that the average gamer would spend 80ish hours to noodle around in that virtual environment. That’s a lot of “life spend.”

And unlike many other video games, it’s time spent, well…alone.

GTA 6 has no multiplayer mode as of this writing (though it could come). This means there’s no opportunity to connect with other people — even remotely — during gameplay. You can’t commit crimes alongside your buddies in the living room; you can’t fire at police alongside friends in Sweden, Hong Kong, or France. You’re alone, for 60 hours, stealing cars and shooting people. You interact only with that world and the characters coded into it.

Now I won’t be entirely obtuse here — not everyone can physically train for a triathlon; not everyone has time or safe access to a place where they can spend 65-150 hours outdoors, even if they wanted to.

However, there is a large proportion of people whose time spent playing a video game (alone) will prevent them from being outside (with others) — moving their bodies through nature in some way, shape, or form.

That’s why, rather than relish the empty streets and bike paths that have been reported across major metropolitan areas this week, I’ll be hoping that once the game ends and the credits roll (do video games have credits?), folks will head back outside to get a refund for time better spent.

I run Lovora, an AI companion service for adults in nine languages. The number one thing people ask an AI companion is "will she remember me?", and "memory" turns out to mean two different things. Here is the design we use, and why.

1. The recent conversation, word for word.

On every reply the model receives the last 40 messages of the chat, both sides, exactly as written. In voice calls it is the last 24, because spoken turns need to be answered faster and the prompt has to stay small.

This layer is what keeps a scene or an argument coherent. A summary would lose the exact wording, the jokes and the thing she promised two messages ago, which is exactly what people notice in a conversation.

Every 5 messages the user sends, a separate pass reads the latest part of the conversation and updates a short list of lasting facts: at most 15 short facts, about 1,500 characters. That list goes into the prompt of every later reply, in chat and in calls.

That is the layer that lets her ask about the job interview you mentioned last week, hundreds of messages later.

Small talk is discarded. A fact that is contradicted later is updated or dropped, not appended: the list is rewritten, not grown. The character is told to use what she remembers naturally, by asking about it or referring to it, and never to recite it as a list. Reciting is the fastest way to make a companion feel like a database.

A small fixed budget forces the distillation step to decide what matters, which is exactly the judgment retrieval skips.

In a Midtown Office, Artists Sift Through the Junkspace of Capitalism

📅 Nov 20, 2026  |  Category: Technology  |  Read Source →

An intergenerational group of artists confronts technology as both a pathogen and a cure for today’s cultural ailments in the husk of an office at 260 Madison.

A few hours before 260 Madison opened on September 24, I trekked to its namesake address in Midtown to meet the curators. A security guard directed me to the 14th floor of the 1950s office building, where drop ceilings, an exposed HVAC system, and two people I assumed were the exhibition organizers dressed in corporate drag greeted me. They quickly clarified they were not; they were from AmTrustRE, the real estate company that offered the derelict 23,000-square-foot office space to the artists for free while preparing it — and three other unoccupied floors — for their next corporate tenants.

The three artists-turned-curators, Shaina Tabak, Dayana Matesheva, and Edison Niebla Rodríguez (the latter two of whom make up the duo DemonLovers Inc.), organized 260 Madison as an intergenerational, “inter-everything” show with work by over 50 artists, including self-taught and non-traditionally educated practitioners. On view through this Sunday, November 22, the show arrives just as the Whitney Museum of American Art opens artport: A History of Internet Art, signaling a new wave of institutional recognition for internet-grown art. With 260 Madison artists Maya Man, Rachel Rossin, and Eva and Franco Mattes among those included in the Whitney’s 25th-anniversary exhibition for its net art commissioning platform, the Midtown show feels especially urgent, if only because it takes place at the precipice of a paradigmatic shift within the art world.

Upon entering the first room on the left, I was immediately met with artist Jon Kessler’s towering nine-foot-tall sculpture, in which four plastic male dolls in Adidas tracksuits dangled from a weighted contraption somewhere between a carnival ride and a torture device. Titled “It Takes a Global Village Idiot” (2018) after philosopher Marshall McLuhan’s early ’60s theory that information-age technology “recreates the world in the image of a global village,” the sculpture forces viewers to confront the fact that the quick fixes of amusement proffered by technology rely on the same methods of data extraction that undergird systemic violence. It’s an unsettling introduction to a show where, even in its more humorous, delusionally conspiratorial, or enchanting moments, discomfort is always in the periphery.

“We don’t want to make a show or art that tries to be some form of escapism,” Rogríguez told Hyperallergic during an interview the week after the opening. “It’s like the [Werner Herzog] quote, ‘The poet must not avert his eyes.’ If some art in the show seems depressing, it’s because we live in what seems a depressing time.”

Rodríguez and Matasheva, who are also a couple, began making work together seven years ago while studying film in Montreal. Their video-art duo is named after Olivier Assayas’s 2002 film Demonlover, where multiple global corporations compete for a new immersive Japanese hentai company through extreme methods of espionage, exploitation, and blackmail.

“DemonLovers is about the libidinal economy and how algorithms are weaponizing our very basic instincts and desires,” Matasheva told Hyperallergic, echoing Rodríguez’s interest in what he calls “financial Freud,” or the psychoanalytic dimension of digital capital flows.

Both DemonLovers’s own two works in the show and those they curated certainly don’t shy away from the degradation associated with extractive economies, be it of the self, physical infrastructure, or the proverbial global village. Nearby Kessler’s work, Theresa Tomi Faison’s “The Long Tail” (2026) climbs up one of the floor’s load-bearing columns. Across the curved sculpture’s six screens, images of memes, forum screenshots, and phrases ruminating on contemporary capital flow all accumulate and dissolve downstream. The river of digital spam ends at the viewer’s feet, inculcating the audience, but also the space itself, which the curators characterize as shaped by "junkspace,” which architect Rem Koolhaas describes as the fallout that “remains after modernization has run its course.”

Among works that are either readymades or play with the form’s history — including Anthony’s Discenza’s windowsill pile of unopened credit card and loan offer letters in “Offers” (2026) and Eva and Franco Mattes’s distended taxidermied cat, “Longcat” (2026) — the corporate detritus can be difficult to parse from the artistic interventions. At one point, I mistook a few square feet of wallpaper with the Champion logo for a new work. The curators clarified during a later conversation that it was actually kept from the office’s previous tenants, HanesBrands, which owns Champion.

Having also inherited the space’s trove of gutted bathrooms, broken drywall, and stripped concrete floors (in short, its junkspace), the curators said they view 260 Madison through “layers of site responsiveness” more than anything. With some works, that connection emerged during the eleventh hour of installation. With others, the site occasioned the work itself. Ivana Dama used exposed air vents for “The Air Was Already Here” (2026), a sound work that channels air through reeds, transforming the invisible, inaudible rhythms of the space into what the artist describes as a “sculptural presence.” Pictures Generation artist Matt Mullican took a 47-foot span of unused wall space as an opportunity to reflect on his five-decade practice of constructing, deconstructing, and classifying systems of representation and perception with largely nonverbal symbols.

“He spent three days here drawing his entire practice on the wall, right from the beginning to the end,” Matasheva said regarding Mullicant’s monumental graphite piece, “Representing The Work” (2026). “He said he will give a lecture about it and that it's a very important work for him. It's kind of a conclusion of his practice.”

Meanwhile, the show’s video works are lodged into broken columns, ceiling alcoves, liminal backrooms, bathroom plumbing, abstract paintings, and even a hanging pink punching bag, a veritable reunion of the last decade of post-internet art movements. Alumni from Joshua Citarella’s publishing platform Do Not Research, the New Museum-affiliated Rhizome, and the traveling video and film screening series Open Secret, including Faison, Dana Dawud, Yehwan Song, and Ruba Al-Sweel, have contributed works. Many of them feature themes of surveillance, internet-induced conspiracy, and social media performance, as well as the technological, often AI-abetted methods of production that have come to define such enclaves.

Yet, for all the immateriality and speculative knowledge that flows through these works, 260 Madison equally plumbs an idea of technology with a long, craft-driven history. Tabak, a sculptor with a background in furniture design, is the driving force behind this facet of the show — and the currents of divination, enchantment, and even sublimity that come with it.

“My practice is very handmade and material-focused, so I always know that that’s what I would contribute to the curatorial vision,” Tabak told Hyperallergic. “And just being in Midtown, you shouldn’t separate a show from what’s happening around it.

Tabak was particularly interested in curating works that “blur the line between the hand and technology,” inviting artists who “haven’t had a lot of chances to show in art contexts, whether it’s because they are in the design world or have nine-to-fives” to participate in the exhibition. She explains that many of them complicate the very notion of technology and its use, citing Brian Oakes’s “Vessel 9” (2025), which gathers 3D-modeled circuit boards into a suspended “techno-Gothic” chandelier, and Ryan Decker’s “The Wavemaker Falters” (2026), which uses a motorized, rudder-like instrument to swoosh water through a raised vessel resembling a spaceship.

“We view technology not as something that has arrived in the 20th century, but something that has made humanity possible,” Matasheva said, expanding on Tabak’s comment. “Language is a technology, a chisel is a technology, everything is a technology.”

While many of the show’s craft-driven works conjure the anthropologist Alfred Gell’s idea that art is a technology that enchants, and in turn, becomes enchanted, others wield technology in the service of care. Kylie Mitchell repurposes a light-seeking solar robot and discarded electronic parts to move a found bird’s nest and egg toward a life-sustaining heat lamp. A few dozen feet away, Gregory Kalliche’s installation “Black-tailed gull nest; Ring-necked Pheasant Nest; Mallard Nest” (2016) suspends an LED light over three metal folding chairs printed with images of bird egg nests. Ben Gould’s “Ark II” (2026), on the other hand, augments a hospital gurney with eight aluminum armatures that hold fresh red roses inside coil-shaped glass vials. Doubling as a literal manifestation of Shakespeare’s “this mortal coil” phrase in Hamlet, the sculpture’s sterile infrastructure butts against the transitory visual comfort proffered by its flowers, mirroring a healthcare ecosystem wherein privatization, optimization, and tech automation have whittled medicine’s promises of care, healing, and empathy into mere aesthetic veneers.

It’s no coincidence that many of the works in 260 Madison position technology as both a pathogen and cure for today’s cultural ailments. In fact, when the real estate developers initially contacted Columbia University’s School of the Arts, it was to invite artists to “activate” a 36,000-square-foot gutted Duane Reade on the building’s ground floor. The developers eventually retracted their offer and moved the exhibition to the 14th floor, citing ongoing construction. Meanwhile, the original plan for 260 Madison to occupy the husk of the Duane Reade will be realized in a different form next month. Now serving as the building’s new temporary lobby, the former pharmacy will play host to a different group exhibition curated independently by Tabak. Opening December 3, HOW I FEEL will feature artists working across sculpture, social architecture, photography, painting, performance, and programming, including Jessica Vaughn, Quay Quinn Wolf, André Magaña, and 260 Madison’s Grayson Cox and Luke Murphy. How the forthcoming Duane Reade show contends with this moment of tech-induced economic entropy, so intense that even an entity as extractive as a real-estate company cannot commit to its own speculations, remains to be seen.

How to Run Long-Running AI Agents in Production (2026): Runtime Limits, Durable State, and Surviving Restarts and Outages

📅 Nov 20, 2026  |  Category: Technology  |  Read Source →

Posted on Nov 20 • Originally published at controlplane.com • AI-assisted

Long-running AI agents need three things that serverless request handlers do not give them: a process with no short execution cap, state checkpointed outside the process so a restart resumes from the last step, and presence in more than one location so a provider outage does not stop the agent. Most teams find these gaps after a prototype works in development. In production it dies mid-run when a function times out at 15 minutes, a deploy kills the container, or a zone goes offline.

Disclosure: Control Plane publishes this guide.

Long-running AI agents fail in production when the infrastructure treats them like short-lived request handlers.

Production agents need a runtime that does not stop them after a few minutes, a state layer that survives process death, and enough redundancy to stay up through infrastructure failures.

Execution limits vary widely, and hitting a cap mid-run loses work unless a durable layer sits on top.

Short-lived serverless functions need a durable execution layer on top, and long-running container runtimes still need graceful shutdown and external state.

The right state layer depends on your existing infrastructure, how complex the workflow is, and how long the agent needs to pause.

A team that already runs Postgres can add durability with DBOS or the LangGraph Postgres checkpointer and little new infrastructure. Complex multi-day orchestration with many branches fits Temporal. The OpenAI Agents SDK documents integrations with Temporal, Restate, DBOS, and Dapr for long-running agents, and the OpenAI Responses API background mode runs long requests that are polled or delivered by webhook. A single cloud’s durable service keeps agent state inside that provider’s failure domain, so a provider outage stops the workflow along with the agent.

Eleven failure modes regularly stop production agents, and each has a control that prevents lost work.

Every control depends on state living outside the process and outside any single failure domain.

Graceful shutdown, rolling updates, multi-location replicas, and checkpoint resume work together.

When a deploy, scale-in, or node drain happens, the orchestrator sends SIGTERM to the container. The agent should catch it, stop picking up new steps, and complete or checkpoint the current step. A preStop hook runs before SIGTERM, and its time counts against the termination grace period, which defaults to 30 seconds on Kubernetes.

Rolling updates keep capacity during deploys by replacing replicas in batches (on Kubernetes, by default no more than 25% unavailable at once) and waiting for each new replica to pass readiness probes. A PodDisruptionBudget limits how many replicas are down at once during voluntary disruptions such as node drains; it does not throttle a Deployment’s own rolling update.

Multi-location replicas protect against zone, region, and provider outages. If the agent runs in two locations and one fails, the other keeps serving. Checkpointed state must live in a store the surviving replicas can reach, such as a Postgres database replicated across regions. Asynchronous replication can lose the latest checkpoints on failover, so the resumed step must be safe to repeat, and leases belong on one strongly consistent primary at a time. When that primary’s location fails, promote a replica in a healthy location and advance the fencing epoch so writes from the old primary’s era are rejected.

Resuming from checkpoints ties these together. A replica in a healthy location loads the last checkpoint and continues. Steps whose completion was recorded are skipped, the interrupted step runs again, and idempotency keys let that retry run without duplicate side effects. Routing users to the nearest healthy region covers the traffic side.

Control Plane handles Day 2 operations for you, including autoscaling, built-in observability, and security.

It runs five workload types: serverless, standard, stateful, cron, and VM. On Control Plane, standard workloads are long-running processes, so an agent runs continuously with no execution cap. Stateful workloads give each replica a stable identity and its own persistent volume; a replica keeps the same identity (such as agent-0) when it is restarted or rescheduled, each replica is bound to its own volume from a volume set, and volume sets support snapshots. An inbound HTTP request times out after at most 600 seconds, or up to 3,600 seconds with the cpln/timeoutSecondsOverride workload tag, so run longer agent tasks as background work in the workload, with clients polling for status or receiving a callback.

A Global Virtual Cloud (GVC) is Control Plane’s named set of locations across AWS, GCP, Azure, and Oracle Cloud Infrastructure regions, plus your own Kubernetes clusters. A workload runs in every location of its GVC. Each workload’s endpoint routes clients to the nearest location where it passes readiness probes, so when one location fails, traffic reaches the healthy ones. In-flight work in the failed location resumes elsewhere only if its state was checkpointed to a store the other location can reach and its lease has expired; the fencing token on checkpoint writes keeps a cut-off replica from committing progress for the same run, and idempotency keys keep its side effects from repeating.

For that store, Control Plane’s Template Catalog includes PostgreSQL, PostgreSQL HA, and multi-location databases such as Postgres Multi-Location and pgEdge, which can back DBOS, the LangGraph Postgres checkpointer, or a custom checkpoint table; keep lease and fencing writes on a single primary, because multi-master replication resolves conflicts after the write. Temporal is also in the Template Catalog for teams that orchestrate with it. By default each replica gets a 90-second termination grace period, configurable in the workload’s rollout options.
