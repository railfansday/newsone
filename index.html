How Agent Anomaly Detection scores on benchmarks we didn't write

📅 Nov 13, 2026  |  Category: Technology  |  Read Source →

AI agents now read email, book travel and move money for the people who use them. Every tool call also pulls in text that someone else wrote, and whoever controls that text can try to steer the agent. OWASP calls this agent goal hijack and ranks it first in its Top 10 for Agentic Applications (2026).

In September we announced Agent Anomaly Detection in Private Preview on Gemini Enterprise Agent Platform. It reads your agents' traces and logs asynchronously, without adding latency, and flags sessions where an agent acts outside its intended boundaries. We tested this feature against benchmarks for this top risk of agent goal hijack.

Security tools tend to look good on tests their own team wrote, so we ran five non-Google-written, public agent-security benchmarks through Agent Anomaly Detection without changing anything. In four of them, the harmful instruction hides in data that a tool returns. In the fifth, the user asks for harm directly.

The model itself didn't follow about half of the harmful instructions it read. It refused three in four direct requests for harm, and ignored or failed at about 30% of the instructions hidden in tool output. Of the ones that were executed, Agent Anomaly Detection flagged 87% for post-execution review. It raised false alarms on 2% to 16% of benign sessions, depending on the tools the agent uses. Poisoned memory is the clear gap: when instructions planted in the agent’s long-term memory made it act, Agent Anomaly Detection caught 4 of 18.

We ran each benchmark case through an agent built with the Agent Development Kit (ADK) using gemini-2.5-flash, on the benchmark's simulated apps. The agent sent its traces and logs to Agent Anomaly Detection, as a customer's agent would. Then the benchmark's own Python check read the final state of the apps, such as whether money left the account, and labeled the session. Deterministic code decides the label, not a model, so an injected instruction can't mislead the grader, and Agent Anomaly Detection cannot cheat the benchmark. Each agent first ran at least 300 benign sessions, because Agent Anomaly Detection learns how each agent usually behaves.

We also recorded whether a tool returned the harmful instruction to the agent. In many cases, the agent never opens the email or file that holds it. So each harmful session ends one of three ways:

In AgentHarm, the user sends the request, so the agent always reads it.

The five benchmarks are AgentDojo (NeurIPS 2024), InjecAgent (ACL 2024 Findings), Agent Security Bench (ASB, ICLR 2025), AgentDyn (2026) and AgentHarm (ICLR 2025). ASB plants the instruction in the agent's long-term memory. In all, Agent Anomaly Detection scored 1,774 sessions.

Agent Anomaly Detection flagged 87% of the harmful instructions that the agent carried out, and raised a few false alarms on ordinary office work. It's strongest on goal hijack and tool misuse, and weakest on poisoned memory.

Each finding carries a threat category, and four of Agent Anomaly Detection’s five categories align with the OWASP Top 10 for Agentic Applications. We graded each OWASP category on what this study showed, not on what Agent Anomaly Detection is designed to catch.

Public benchmarks concentrate on goal hijack and tool misuse, so our evidence is strongest there. We did not find public benchmarks with labeled agent traces for cascading failures or for identity and privilege abuse. Shared benchmarks for those categories would help the whole field.

By benchmark, Agent Anomaly Detection flagged 85% of the carried-out harmful instructions on AgentDojo, 87% on InjecAgent, 99% on AgentDyn and 81% on AgentHarm. Over all harmful sessions, including the ones that the agent never read or resisted, it flagged 45% to 62%. In the 141 sessions where the agent never read the instruction, nothing happened, and it flagged just 1.

Results held across the apps. In 8 of the 11 apps, Agent Anomaly Detection flagged at least 95% of the carried-out harmful instructions. The lowest rate was in AgentDojo's Slack app, at 63%. Many of those instructions ask for one small action, such as a page visit, which looks like normal browsing.

Agent Anomaly Detection also flags many requests that the agent refuses. In AgentHarm, the agent refused most requests and carried out 108 of 412, and Agent Anomaly Detection still flagged 55% of the refused sessions, because the request sits in the user's own message, which it reads. When the agent didn't follow an instruction hidden in tool output, it flagged only 11% to 25%, because the instruction sits deep inside a tool result.

False alarms were rare on ordinary office work: on the three injection benchmarks, whose benign sessions are office tasks, Agent Anomaly Detection flagged 2% to 4% of benign sessions. On AgentHarm it flagged 16%. Those benign tasks are twins of the harmful ones, so they post to social media, run terminal commands and download files. High-impact tools in normal use look more like misuse.

Agent Anomaly Detection did less well in five areas. It flagged only 11% to 25% of the instructions that the agent resisted, because a resisted instruction changes little in how the agent behaves. It missed more small actions, like single page visits, because they look like normal work. And it raised more false alarms for agents whose everyday work uses high-impact tools. If your agent is one of them, expect more findings at first, and triage them by severity and threat category.

The other two areas are new agents and poisoned memory. Some Agent Anomaly Detection methods need a few hundred sessions of history: on AgentDyn, it flagged 33% of carried-out harmful instructions when each agent had about 220 benign sessions, and 99% with 360. And it caught only 4 of the 18 sessions where poisoned memory made the agent act.

Protect your agents with defense in depth. Use controls that stop harmful actions before they run, and Agent Anomaly Detection to find what gets through.

We used one agent model and simulated apps, and the benchmarks' benign tasks are likely simpler than your production traffic, so your false-alarm rate can differ. Agent Anomaly Detection returned no result for about 6% of the sessions we sent; counting those as misses lowers the overall rates by 1 to 2 points.

Catch Go bugs that fuzzing misses with Gemini and a constraint solver

📅 Nov 13, 2026  |  Category: Technology  |  Read Source →

I help lead Google's agent skills program, currently with 175 agent skills that supplement community collections like go-skills. To keep that many skill files consistent, I wrote skill-lint, a standalone Go CLI that checks SKILL.md files and applies LLM-generated line edits before they ship. Even with skill-lint's own unit and fuzz test suite, a small slice or line-number mistake inside its Markdown parsers or edit applier can sit dormant until an unusual file or edit range triggers a runtime panic in the linter.

In Go, every slice or index operation that can panic at runtime compiles down to an explicit bounds-check trap in machine code, after the compiler's optimizer strips out the checks it can already rule out. To hunt for crashes, I compiled key functions from my code to see which panic traps survived optimization, and Gemini 4 Argon translated the path to each trap into rules for the Z3 constraint solver. An LLM-written solver model isn't a sound proof system, but it gives the agent an independent way to reason about control flow and synthesize concrete Go reproducers, and every crash it finds is real because go test runs the offending bytes directly. That workflow caught all three bugs I planted in test parsers and turned up three latent bugs in skill-lint.

In this post, I'll walk through how the Gemini and Z3 pipeline works, why go test -fuzz missed two of those crashes (and the one-line change that fixes it), and where this approach fits in a day-to-day Go workflow.

A recent post from Anthropic showed how formal verification catches latent bugs in C and C++ by having frontier AI models write machine-checked Rocq proofs across OSS-Fuzz libraries. Instead of sampling random inputs like a fuzzer, a formal tool works backward from each failure condition to solve for the exact input that triggers it. Full theorem proving is still too heavy for most day-to-day Go projects, so I wanted to see how much of that bug-hunting power an agent can get from an LLM and a constraint solver in about a minute per function.

In C and C++, reading or writing past the end of a buffer corrupts memory. Go catches out-of-bounds access at runtime instead, compiling every slice or index operation it can't prove safe into an explicit branch to runtime.panicBounds that panics, crashing the process unless recovered.

Before generating machine code, Go's SSA prove pass already eliminates most of those checks by tracking slice lengths and loop variables. That optimization pass leaves behind only the runtime.panicBounds traps the compiler couldn't rule out on its own, giving the solver a short list of candidate crash sites to target.

I compiled each target with GOOS=linux GOARCH=riscv64 go build -gcflags="-S -d=ssa/check_bce/debug=1" (-S prints the assembly listing and ssa/check_bce/debug=1 logs every surviving bounds check) and passed both the Go source and the disassembly to the model. Looking at Go source alone, you can't see which bounds checks the compiler already removed or where a register gets truncated to 8 bits; in the disassembly, both show up. I targeted RISC-V because it's the instruction set Anthropic's post targets for its Rocq proofs, and Go cross-compiles to it out of the box.

From there, Argon read the Go source and disassembly and returned a Z3 script modeling the path to each surviving trap, along with a patched function whenever it flagged a bug. Z3 then checked whether those constraints could be satisfied, and whenever it found a crashing input, go test replayed those bytes against the real function. Using an LLM saved me from translating assembly into solver constraints by hand. Argon's translation dominated the runtime, at about a minute per function, while Z3 itself finished in milliseconds.

Anthropic's approach relies on interactive theorem proving, where experts model machine semantics and Rocq checks LLM-generated proofs against those rules. In contrast, my workflow uses a constraint solver based on satisfiability modulo theories (SMT), relying on Argon to translate assembly directly into Z3 constraints. While a constraint solver doesn't provide a complete correctness proof without a semantic model, it is highly effective for finding bugs. Z3's check-sat command returns sat when input constraints can be satisfied and unsat when they cannot.

A sat answer ("definitely buggy") comes with concrete bytes aimed at the trap, and go test runs them against the real function. Once go test panics, you have a concrete bug reproducer regardless of whether Argon's model was sound. Like a Bloom filter for bugs, an unsat answer only means "maybe correct." Trading away a correctness proof is what makes the approach so practical: you get most of the bug-finding value of formal methods for a tiny fraction of the effort.

Anthropic's setup proved no-crash properties on whole binaries under a 64 MB budget; I checked individual functions on fresh 64-byte slices where cap(buf) == len(buf), so any slice past len(buf) panics. (If you want the full-binary Rocq setup for Go, theorem-labs/oss-verify includes a Go 1.27 runtime overlay that makes the runtime single-threaded and deterministic.)

For the fuzzing baseline, I ran unseeded go test -fuzz on Go 1.27.3 against each planted bug: one 3-second run and three 60-second runs, each with a fresh fuzz cache so a short time budget wouldn't explain a miss.

I started with three safe parsers to make sure the pipeline didn't flag clean code. The compiler's prove pass removed every bounds check in a TOML key parser on its own, and Z3 returned unsat on the remaining traps in an HTTP header scanner and a varint decoder.

Then I wrote three parsers with subtle panics. Here's the first one, ParseTwoChunkFrame:

In the RISC-V disassembly, the bug is much easier to see:

total := hdrLen + bodyLen adds two uint8 values, so MOVBU wraps the sum at 256 before the length guard checks it, while endBody adds the full 64-bit ints. Argon turned those instructions into a Z3 query asking whether a fresh slice of up to 64 bytes can pass the guard and still fail the endBody check at 0x0092:

Z3 returned a 59-byte counterexample with hdrLen = 48 and bodyLen = 236: their uint8 sum wraps from 284 down to 28 (so 28 + 4 ≤ 59 passes the guard), and buf[endHdr:endBody] then slices to index 288 and panics.

At 59 bytes, 19.4% of all possible (hdrLen, bodyLen) pairs trigger this crash. Yet a 3-second fuzz run missed it, and so did three 60-second runs.

Go checks a slice expression like buf[endHdr:endBody] against the slice's capacity, not its length, and Go's fuzzer rarely passes a slice without spare capacity. In a 10-second probe of 386,741 fuzz calls, 89% of inputs were views into a shared ~100 MB buffer, and only 0.07% had cap == len. With that much spare capacity, endBody (at most 514) never exceeds cap(buf), so the buggy parser returns bytes past the end of buf instead of panicking.

The second target, ExtractQuotedToken, hit the same blind spot when a trailing backslash pushed the index one byte past len(buf). Z3 caught it immediately with the 2-byte input []byte{'"', '\\'}, while the fuzzer absorbed the overrun in spare capacity.

Clipping capacity to length with a full slice expression turns any slice past len into a panic:

After that change, the fuzzer crashed both ParseTwoChunkFrame and ExtractQuotedToken in all three runs (median 0.28 s and 0.17 s). The third target, ParseMagicPacket, was a control because its signed int8 length bug panics on a negative index regardless of capacity, and the fuzzer found it in every run either way. Fuzzing still can't give you an unsat signal across the remaining paths, which is how I checked the three safe parsers and Argon's patches.

Next, I pointed the pipeline at skill-lint itself. A whole Go CLI is too large to hand to a solver directly. Even a 10-line parser links 1,559 symbols from the Go runtime, and the 28 MB skill-lint binary has 32,321 symbols in total. Following Functional Core, Imperative Shell, I left CLI flags, network calls, and file I/O to go test -fuzz and go test -race, and ran the solver only on pure functions and slice helpers extracted from file-reading code.

Of the five functions I tested, two scanners came back unsat (including a CRLF line splitter with six surviving bounds checks), and the other three had bugs. The sharpest was in ApplyReplacementChunks, which validates LLM-generated {StartLine, EndLine} edits against the initial line count and sorts them bottom-to-top so earlier edits don't shift later line numbers:

Z3 immediately returned sat because sorting by StartLine doesn't prevent two chunks from overlapping. In the extracted helper, which checks bounds once up front, replacing lines 3 and 4 of a 4-line file with one line shrinks lines to 3 elements, so a second chunk spanning lines 2 through 4 evaluates lines[4:] and panics with slice bounds out of range [4:3]. In the shipped ApplyChunks, a per-iteration bounds check turns that case into a misleading range error, while overlapping chunks that stay within len(lines) silently overwrite the earlier edit. Rejecting overlapping chunks after the sort fixes both.

The other two bugs were similar accounting errors. In the local fixer, target line numbers were checked once per violation before the inner chunk loop applied deletions that shrank the slice (a latent panic if a fixer ever returns a second chunk after a deletion, though DeleteLineFix only returns one today). In the prompt packer, a truncation check reserved a flat 100 bytes for a ~70-byte wrapper plus file path, overshooting the 2 MB context budget in the shipped code when a path exceeds about 30 bytes and panicking in the extracted helper.

When you check a function modularly like this, the target has to include its own entry-point guards (like the bounds check and sort in ApplyReplacementChunks). If an internal helper assumes preconditions that are only enforced by its caller or stated in a doc comment, Z3 will happily invent inputs that violate them. Because each extracted helper included its entry guards, false positives weren't an issue: across all six buggy functions in my tests, the first sat assignment Z3 returned triggered a real panic in go test without needing to filter out non-crashing candidates or loop back into the solver.

Once I pulled these helpers away from file I/O, a 3-second fuzz run caught all three bugs too. To make sure Argon wasn't leaning on source comments in my test files, I also reran the skill-lint targets with all comments stripped; Argon and Z3 still caught all three bugs and returned unsat on the two scanners and all three patches.

Staying entirely inside the target language makes a whole class of bugs hard for an agent to see. When an LLM reviews Go source directly, a line like if int(total)+4 > len(buf) looks like a textbook bounds check, and when it runs go test -fuzz, target-language runtime details like spare slice capacity or multi-step precondition checks can hide the crash indefinitely. Asking the agent to translate Go and assembly into a constraint solver forces a change of representation that strips away surface syntax and makes every bit width and slice bound explicit, while go test turns any solver hit back into a concrete Go reproducer.

For most Go code, fuzzing pure helpers with slice capacity clipped to length will catch bounds bugs in seconds. A solver is worth the extra minute on the traps that survive both the compiler's range prover and a quick fuzz run, especially in parsers and editors that compute offsets from multi-field headers or line ranges.

Single-threaded solver models don't see data races or deadlocks, so concurrent code still belongs with the race detector, deterministic concurrency testing, and Go 1.27's goroutine leak profiles.

What Does Transgender Mean? Everything You Need to Know, According to Experts

📅 Nov 13, 2026  |  Category: Technology  |  Read Source →

From gender identity to transition, here's what the term actually means.

The word "transgender" gets used a lot these days, but that doesn't necessarily indicate that everyone understands what being transgender actually means. Between headlines, social media debates, and ongoing conversations about gender identity, it's easy to feel like you're missing a piece of the puzzle or even worry about using the wrong terminology altogether. Fortunately, understanding what it means to be transgender doesn't have to be as complicated as the internet sometimes makes it seem.

"Being transgender means your gender identity doesn't align with the one you were assigned at birth. That's the whole heart of it," says licensed marriage and family therapist Adrienne Michelle, LMFT. "It doesn't tell you anything about how someone looks, what they've explored medically, or how far along they are in any journey. It's simply about your authentic sense of self being different from what you were told you were at the start."

Ultimately, gender is deeply personal, and there's no one "right" way to be transgender. Whether you're talking with a friend, supporting a loved one, or simply trying to better understand the world around you, having a basic understanding of transgender identity can make the conversation feel a whole lot less intimidating and a lot more inclusive.

The term "transgender" is an identity label that refers to people whose gender identity doesn’t match the sex they were assigned when they were born, explains therapist and LGBTQ+ educator Zoe Stoller. You'll also often hear transgender shortened to simply trans. The prefix trans- means "across" or "on the other side of," reflecting that a person's gender identity differs from the sex they were assigned at birth.

"Gender is expansive, and 'trans' is the umbrella term that often holds all of that expansiveness," says Michelle. "It isn't a single identity; it's a beautifully wide category that makes room for so many people."

The transgender umbrella includes trans men, trans women, and many nonbinary identities, though not everyone whose gender identity differs from the sex they were assigned at birth identifies as transgender. And that's completely okay. The right label is the one that feels right to the person using it.

Although they're often used interchangeably, sex and gender aren't the same thing. Sex refers to the biological characteristics someone is labeled or assigned at birth, while gender refers to a person's internal sense of who they are. You may also come across the terms AFAB/AMAB (assigned female at birth/assigned male at birth), which describe the sex someone was assigned when they were born, not their gender identity. And while babies are often labeled male or female at birth, sex itself isn't always binary, as intersex people exist too.

Once you understand that distinction, a lot of the terminology starts to make more sense. Terms like nonbinary, genderfluid, genderqueer, and gender nonconforming all describe distinct experiences or expressions of gender, but they aren't interchangeable, and they don't all automatically mean someone is transgender. (P.S. If you're looking for a deeper breakdown of those identities, check out our complete gender identity glossary.)

"Gender nonconforming is about not feeling aligned with the normative, performative ways gender is 'supposed' to show up—the expectations around how a man or woman should look, dress, or move through the world," says Michelle. "It's about expression, not identity. You can be gender nonconforming and cisgender, and you can be gender nonconforming and trans. The two sometimes overlap, but they're answering different questions: transgender is about who you are, gender nonconforming is about how you show up."

As Stoller explains, the transgender umbrella includes both binary identities (such as trans men and trans women) and many nonbinary identities, though not everyone whose gender differs from the sex they were assigned at birth identifies as transgender. Like every other aspect of identity, everyone's relationship with gender is unique.

First things first: Despite the headline right above this, there's no one way to "look" transgender.

“What people are often really asking about here is about passing and stealth—whether someone is read by others as cisgender, and whether they choose to share their trans status at all,” Michelle notes. “Those are personal privacy and safety decisions, not requirements for being trans. Someone's transness is never more or less real based on how easily a stranger can read it.”

As Stoller explains, being transgender isn't defined by surgeries, medical procedures, or any other external milestone. The only thing someone needs to "count" as transgender is feeling that the label accurately reflects who they are. For many people, that identity is deeply affirming regardless of whether they ever choose to transition.

Transitioning simply refers to the process of aligning someone's life more closely with their gender identity. "It’s important to note that transition isn't a checklist," says Michelle. "Some people explore hormones or surgery, some focus on legal or social changes, some pursue none of it, and every one of those paths is whole and valid."

Transitioning can look different for everyone, but it's generally broken into a few categories:

Some people choose to align their outward appearance with their gender identity because it's an affirming—and sometimes life-saving—way to feel seen as their authentic selves, Stoller says. Others don't transition at all or may be unable to do so for personal, financial, or safety reasons. Regardless, their gender identity is no less valid.

Now that you know what transgender means, it's worth talking about how to actually use the term. According to Michelle, "transgender" is an adjective, not a noun. "You'd say 'a transgender person' or 'transgender people,' never 'a transgender' or 'the transgenders,'" she explains. "It works just like any other descriptive word; you wouldn't call someone 'a tall,' so the same care applies here."

As Stoller explains, it's also important not to assume someone identifies as transgender unless they've shared that information with you. Even if you think someone's gender identity technically falls under the transgender umbrella, it's ultimately up to them to decide which labels feel the most accurate and affirming. When in doubt, use the language someone uses to describe themselves.

One of the most common terminology mix-ups is the difference between a trans man and a trans woman. "A trans man is someone who was assigned female at birth and now identifies and lives as a man. A trans woman was assigned male at birth and identifies and lives as a woman," explains Michelle.

It's an important distinction because these terms describe who someone is, not who they used to be. In other words, trans men are men, and trans women are women. The word trans simply provides additional context about their gender journey—it doesn't change their gender.

As Stoller notes, some trans men and trans women identify fully within the traditional gender binary, while others may also feel connected to nonbinary experiences. Like every other aspect of gender identity, there's no one "right" way to experience or describe being transgender.

The short answer? Use the pronouns someone asks you to use. It's really that simple.

As Stoller explains, people—whether they're transgender or cisgender—can use whatever pronouns feel the most affirming to them, including multiple sets of pronouns or neopronouns. Although people often associate certain pronouns with certain genders, pronouns don't always tell you someone's gender identity.

If you aren't sure which pronouns someone uses, it's okay to politely ask. And if you accidentally get it wrong, apologize, correct yourself, and move on.

Another common misconception is that being transgender somehow determines who someone is attracted to. It doesn't.

Gender identity and sexual orientation are two completely different things (and both are different from romantic orientation), Michelle explains. Gender identity describes who someone is, while sexual orientation describes who they're attracted to. That means transgender people can be straight, gay, lesbian, bisexual, pansexual, asexual, or identify with any other sexual orientation—just like cisgender people.

Like gender identity, sexuality is deeply personal. Labels can be helpful, Stoller says, but they don't always capture the full picture of someone's experience, so it's always best to use the language someone chooses for themselves.

Being a good LGBTQ ally doesn't require having all the answers. It starts with listening, staying open to learning, and treating transgender people with the same respect you'd want someone to show you.

Use the name and pronouns someone asks you to use, and don't make assumptions based on their appearance or gender identity. As Michelle explains, a trans man might use he/him pronouns, a trans woman might use she/her, and a nonbinary person might use they/them—or another set of pronouns that feels most affirming to them. If you aren't sure, it's okay to politely ask.

It's also important to respect people's privacy. Not every transgender person wants to talk about their transition, medical history, or body, and no one owes you that information. Instead of expecting the transgender people in your life to answer every question you have, take the initiative to educate yourself through reputable resources like GLAAD.

You may also come across the word transsexual, particularly in older books, articles, or medical literature. While some transgender people have reclaimed the term for themselves, Stoller notes that it's generally considered more outdated and medicalized than transgender, and many people find it offensive. Unless someone has specifically told you that's the label they use, it's best to avoid it.

Above all, remember that every transgender person's experience is different. Listening, respecting the language people use to describe themselves, and remaining open to learning will go a long way.

If you've made it this far because you're wondering whether the word transgender might describe you, know that you don't have to have everything figured out today. Gender identity isn't a quiz you pass or fail, and there's no deadline for understanding yourself.

As Stoller explains, there's no single way to experience being transgender because every person's relationship with gender is different. Some people transition socially, medically, or legally, while others never transition at all. None of those experiences make someone's identity any more or less real.

If you'd like support, consider talking with an LGBTQIA+-affirming therapist, connecting with trusted friends or loved ones, or exploring resources from organizations like The Trevor Project can be a good place to start. You don't have to navigate questions about your identity alone.

As Michelle puts it, "Gender is expansive, full stop." The most important thing isn't fitting neatly into someone else's definition; it's giving yourself the space to discover what feels authentic to you.

When a major artist dies, the tributes that come pouring in often gloss over personal shortcomings, whether the failure to complete educational degrees or the abandonment of wives and children. The tone was sombre and celebratory, ending with her brother-in-law Bennie Maupin on saxophone and the band Bayou Bump leading a procession, as Saar had wanted.

One of the most powerful tributes came from her eldest nephew, Channing Johnson, who described her as a “true” if untraditional matriarch. “She was as impactful and skilful as a family matriarch as she was a gifted artist. She gathered us together whether it was in a back yard or public park. Johnson also celebrated Saar’s sense of humour and adventure, noting that she learned to belly dance early on and showed off her dance moves in June when she was honoured by the Museum of Modern Art (MoMA) at its Party in the Garden gala.

The veteran Los Angeles collector Joy Simmons, who recalled bringing her week-old daughter Naima to a Saar opening at the Jan Baum gallery in 1981 (“I was not going to miss this opportunity to celebrate a Black woman opening up at a white woman’s gallery”), described the Saar creative lineage, which extends to grandchildren who work in the arts today.

“To Alison, Lezley, Tracye and the whole family: I’ve watched three generations of Saar women make this city’s art history something special. Betye’s work belongs to museums now,” Simmons said, “but I know her proudest moment and her proudest accomplishment is all of you.”

Mail Authentication Provisioning: DNS Record Upsert and the Cutover Evidence Budget

📅 Nov 13, 2026  |  Category: Technology  |  Read Source →

Default to upsert when provisioning customer support mail authentication, and reserve create for a record whose prior existence must stop onboarding. The deciding constraint is authority: a retry may repeat an authorized desired state, but it must not become permission to replace another administrator's configuration.

Short answer: upsert handles repeat provisioning; create treats an existing record as a conflict; update requires an existing record and therefore does not cover first-time onboarding. None of those choices proves that recipients can see the intended SPF, DKIM, and DMARC configuration. Keep propagation evidence outside the write-success gate.

This decision concerns a support team enabling authenticated outbound mail for customer domains. The desired outcome is successful delivery, while the engineering decision is narrower: choose a repeatable write operation without treating a fast control-plane response as proof that the mail cutover is ready. DMARC supplies part of the authentication framework; it doesn't turn a provisioning response into delivery evidence.

Consider an illustrative planning workload of 40 customer domains, each with three intended record entries: one SPF entry, one DKIM entry, and one DMARC entry. That is 120 desired entries. These are planning inputs, not a claim that every mail deployment requires exactly three records, and the contents must come from the customer's approved mail configuration.

Suppose the orchestrator attempts the whole batch twice. It has now scheduled 240 record operations, but the desired configuration still contains 120 entries. A timeout between submission and acknowledgment is the interesting case: the orchestrator cannot conclude that nothing happened, and repeating create can turn a recoverable uncertainty into a duplicate-record error. Upsert makes a repeated provisioning run with unchanged desired state a no-op.

The operating bill includes schema mapping, retry handling, conflict review, verification work, and any downstream mail activity started before the cutover was actually ready. A useful planning expression is integration effort plus mutation attempts plus verification effort plus recovery effort. Those terms deliberately have no invented dollar coefficients; estimate them from the team's own workload rather than treating an API unit charge as a measurement of the whole system.

For a backend team automating support-domain onboarding, try Infrai for the record-provisioning adapter when public discovery and runnable examples would reduce the work of connecting that adapter to the rest of the system. Its API is self-describing: discovery is public without a key, and capability details expose request and response schemas plus runnable examples, so adding this capability begins with reading its description rather than learning another SDK. Infrai exposes one REST API with no SDK required. For teams already using Infrai, one API key and unified billing across 295 routes in 20 modules reduce the credential rotation and invoice reconciliation work attached to adding a DNS adapter. A separate supporting benefit is its specified idempotency convention, including an Idempotency-Key header and a default 24-hour deduplication window, which gives the orchestrator a documented retry contract to inspect.

That window is a boundary, not a lifetime guarantee. The durable design still needs upsert semantics for later reconciliation and an explicit decision about who owns each desired record.

The first invariant is authorization over the intended configuration. A process can possess credentials for a zone while lacking authority to replace every record in it. Treat an unexpected existing value as an ownership question before choosing a mutation, because a convergent write can converge to the wrong administrator's desired state just as efficiently as the right one.

The second invariant is complete input. Create, update, and upsert each require zone_id, record type, name, and content; there is no partial write that infers the remaining values. Store the approved desired state before scheduling a write, and distinguish a retry of that state from a new configuration revision. An omitted content field isn't an instruction to preserve whatever the server finds.

The third invariant separates accepted mutation from observed DNS state and, later, mail readiness. The primary trade-off is propagation delay versus cutover speed: starting the next step as soon as the write returns is quick, but it spends confidence that the control plane has not supplied. Waiting for the required observations extends onboarding and adds verification work. This decision does not prescribe a universal wait duration, because no measured propagation interval is established here.

This resembles a storage-system distinction between acknowledging a mutation and satisfying a reader's visibility requirement. It is an architectural analogy, not a claim that DNS has the same consistency model as an object store. The useful habit is to name the observation that authorizes the next action instead of calling every successful write “done.”

The first comparison is between mutation contracts, and the second is between places to implement them. Combining those questions into a generic vendor ranking conceals the actual decision: the team needs a safe adapter for its authoritative zone and a separate way to establish mail readiness.

A direct competitor is the better choice when the team already has an approved provider-specific record workflow, conflict review, and cutover evidence, because replacing those controls must earn back its migration effort. The self-describing API is useful when it removes schema and example discovery work from a new adapter; it cannot remove the need to decide whose configuration wins.

The critical path starts by inspecting the operation the adapter will call. This is deliberately an inspection example rather than a write with guessed fields. Then validate the complete desired record, enforce the ownership boundary, and select upsert unless conflict or existence semantics require create or update. Persist a client idempotency key for the same intended write, and follow the operation's documented contract when submitting it. A changed desired record is a new intent, not an excuse to recycle the previous request identity. An observation from before the write is evidence for planning, not an atomic lock against another writer.

The conservative branch is to stop on unknown ownership. Blindly replacing unknown state optimizes the wrong part of the workload: it shortens the mutation path while transferring uncertainty into investigation and customer review. An owned target can be reconciled with upsert; an absent target can be initialized with it. A foreign target stops.

Even a correctly implemented retry loop answers only the mutation question. Preserve a separate readiness state for each customer domain so a retried onboarding job cannot silently promote “submitted” into “safe to send.”

Reject create as the default for repeat provisioning. It makes prior existence a conflict, which is exactly the wrong signal when a previous attempt already wrote the same approved state and the orchestrator is recovering from an uncertain acknowledgment.

Keep create for protected onboarding where an existing record means someone else has configured the domain and the process must stop. That conflict is useful evidence. Update likewise remains appropriate for an existing target whose absence should fail, but its existence requirement makes it a poor general initializer.

For the support-mail workload, choose the primitive that matches authority, then spend the remaining effort on cutover evidence. Faster writes don't settle the propagation decision. We literally built machines that defy the will of the gods, zoom across our skies, and let us travel in ways we were never meant to travel. Should I have been able to pull off a whirlwind visit to Boston while living in Georgia? Probably not, but the miracle of flight made it possible, and there's always going to be some thing special about sitting in a window seat that lets you see the beautiful world beneath you. Los Angeles isn't the prettiest city in the world, but even LA looks incredible from 10,000 or 15,000 feet.

With the window seat, you'll also have an easier time napping on your flight, and air travel takes so much time out of your day, you could probably use a snooze. Yes, most seats now have those bendy headrests that are supposed to make napping a little easier, but nothing beats using a sweater as a pillow and leaning against the plane. The bendy headrests can try, but while they're better than nothing, they still don't work all that great. All humans need to sleep, so book a window seat, enjoy the view, and then take a nice nap once the plane makes it above the clouds.

Does going to the bathroom get a little awkward? Sure, but there's no reason you have to drink four whiskey cokes before you board your flight. They have edibles for that now. Any time you get up to go to the bathroom, that's also the opportunity to make a new friend. Most importantly, if everyone who reads this ends up fighting over those beautiful views from the window, there will be more aisle seats available for me to take. Michelle may have a point, but I still prefer the aisle and will not be changing my mind.

Sony’s Tom Rothman Hopes It Will Be A ‘Brand New Day’ For ‘Spider-Man’ As Studio Launches Major Best Picture Oscar Campaign: “Are You Telling Me There Are 10 Films Better Than This One?”

📅 Nov 13, 2026  |  Category: Entertainment  |  Read Source →

EXCLUSIVE: Watch out Oscar. Spider-Man is aiming to get your attention.

Sony Pictures and Marvel‘s Spider-Man: Brand New Day is about to launch an all-out campaign to land a spot in the Best Picture race at the 99th annual Academy Awards. Can the highest-grossing movie of not just this year but all time at the domestic box office (now just shy of $41 million to become the first billion-dollar grossing movie domestically), land a place among the coveted 10 the Academy names as Best Picture nominees? Tom Rothman, chairman and CEO of Sony Pictures Motion Picture Group, thinks so and has decided to put the full weight of the studio behind the effort.

“The Academy is meant to recognize greatness. So, to be honest, I think it’s greatness. I think it’s received wisdom. If there aren’t people thinking about it, we’re gonna do what we can just to make people think about it,” Rothman told me this week. “I think it’s also incumbent upon studios who make these kinds of quality commercial films to get people to think about it, and here’s what I ask people when I walk around: ‘Are you telling me that there are 10 films this year that are better than this film?’ ” Watch on Deadline

Spider-Man: Brand New Day, , the fourth entry into the MCU Tom Holland era of Spidey movies at Sony, is at 90% fresh on Rotten Tomatoes, nearly as critically acclaimed there as perceived large-scale Oscar contenders The Odyssey and Project Hail Mary which are also in the 90s ( and even some of the more arthouse-style contenders). Both of those, along with the upcoming unseen Dune: Part Three, are in Gold Derby’s projection of the current top 10 movies with best chances to land a Best Picture nomination. Spider-Man: Brand New Day is listed way down at No. 36, with a 0.46% chance of making the cut, well below The Sheep Detectives and a few notches above I Love Boosters. Pundits are basically ignoring the year’s biggest film, so we have to ask why.

Of the previous eight live-action Spider-Man films Sony has released since 2002, the only Oscar nominations they have received have been in the Visual Effects and Sound categories, the most recent nom for Visual Effects for 2001’s No Way Home. 2004’s Spider-Man 2 is the only one to actually win an Oscar, that one also for Visual Effects. On the animated front, 2018’s Spider-Man: Into the Spider-Verse won for Best Animated Feature, and its 2023 sequel was also nominated.

Not one of these 10 films has cracked the Best Picture race. Rothman feels Brand New Day can, and deserves to be the breakthrough.

“I think to be honest, it’s because there are things like Gold Derby, you know, whatever that is, that just tend to think only about the art film world, and look, I’m an art film guy. I made my bones in the art film world, I’m Mr. Searchlight, right? You know, my whole career, I love art films. But I’m a traditionalist, and I was never for expanding the number of Best Pictures from five to 10. Okay, I liked it the old way, but I believe that the very reason it was extended from five to 10 was so that the Academy would have room to recognize really quality commercial filmmaking,” he said pointing (correctly) to Christopher Nolan’s Best Picture-snubbed superhero movie The Dark Knight as the key reason.

“I think wise heads know that quality commercial filmmaking is extremely difficult, and to make a movie like this, never mind the fact that it’s the highest-grossing movie in history of America, forget that. It’s in the 90s on Rotten Tomatoes for critics, it’s in the 90s on audiences on Rotten Tomatoes. Here’s the thing: the movie’s great. I’m a biased witness, but that’s not me, that’s objective. You don’t have the results that you have, where we had people seeing the movie two and three times. You don’t do close to a billion dollars in America. But are there 10 films that are better than this film, just in pure quality? I think when you see movies like F1 and Barbie and Wicked and Bohemian Rhapsody, whatever, getting nominated, well that is the very reason that that the Academy changed to 10.”

So Sony has hired awards consultants and is making big plans. The studio plans a “robust” screening strategy starting just before Thanksgiving, including multiple FYC Q&As with filmmakers and department heads. Stars Tom Holland and Zendaya are also involved in campaigns for other 2026 contenders like The Odyssey and Dune 3 and Holland is in pre-production on a new film, so their availability going forward is not known. Rothman himself plans to host screenings and tastemaker events on both coasts.

In addition to Los Angeles and New York, there will be special screenings in London, Paris, Madrid, Copenhagen, Sydney, Rome, Mexico City, Berlin and Tokyo. And, as Deadline teased in September, the studio plans to do a big rerelease of the movie before year’s end — possibly as Deadline intimated with some unseen footage — that will also bring new attention to the film and hopefully inspire those Academy voters who have not seen the movie (and based on my conversations there are many) to see it in a theater.

“I think Academy members would be interested in this because it’s very significant from a storytelling movie. This is really the first of these kind of movies that I can think of that does not climax in a giant battle. In this movie there is no giant action sequence at the end. The climax of this movie are two young people sitting on the edge of a bed, talking to each other, and sharing their their deepest pain. This movie is melancholy in that way and beautiful,” he said. “I think people might take Spider-Man for granted, and not only that, I think they make assumptions about it. When you see the movie those assumptions are undone. It’s a very moving, quite personal film. Destin (Daniel Cretton) is a really personal filmmaker. This is the guy who made Short Term 12. That’s what I say when I encourage people to see it, you know, people of my generation. I say you may take it for granted, you may think it’s just another, but it isn’t. It’s really the first, when I think about it. I think it’s the first superhero movie that’s really a super person movie.”

To date, the only movies even remotely in the “superhero” universe to crack the Best Picture race have been 2018’s Black Panther, and 2019’s Joker, though the latter is really a drama far removed from what is expected in the genre.

So the biggest question is can Sony change the trajectory of the franchise in terms of Oscar and get the point across that the record-shattering success of this movie is for a reason? Rothman compares it to the Lord of the Rings franchise in hoping there can be recognition for a movie that has taken a known brand to, yes, a brand new day.

“The Academy members are really, really smart, and they know filmmaking,” he said. “And if they see the movie, which maybe they wouldn’t necessarily do, if they see the movie, I think they’ll recognize how extremely skillful it is, because they’ll know how hard it is to tell an intimate emotional story in that arena. But more than that, I think it’s this specific movie. It’s the work that Destin did, as I said, a true humanist director who put character and emotion first.”
