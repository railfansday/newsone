Self-hosting with Docker, Docker Compose, or Kubernetes adds another question: which environment variables, mounted secrets, and service accounts does the deployment use? A test instance with sample data has a different impact from a production builder attached to customer systems.

For each owned deployment, record the base URL, authentication mode, user roles, workspace membership, data-source connections, outbound network access, and published applications. Separate the builder console from the applications end users are meant to see.

Require strong authentication for the builder and place administrative routes on a private network. Give each connector a least-privilege credential. Do not reuse a database administrator account for application previews or scheduled actions. Test that a user without builder rights cannot enumerate connections or execute an action directly.

Monitor outbound requests from the builder and its action workers. A REST connector can reach internal services if the network policy allows it. Apply an egress allowlist that includes only approved data sources.

Is This Height Comparison Up to Scale? How to Draw One Correctly in JavaScript and SVG

📅 Nov 21, 2026  |  Category: Technology  |  Read Source →

"I've always wondered what a height different between a 4'10 person and a 5'7 person would look like … I found this image but idk if it's up to scale or not."

That question, posted to r/heightcomparison, is the whole genre in one sentence. People want to see a height gap, they find a picture, and then they have no way to tell whether the picture is honest. If you are building the tool that makes those pictures, "is it up to scale?" is the one question your code has to answer correctly every time.

It sounds trivial: multiply height by a constant and draw. In practice, height comparison charts break in a handful of predictable ways: an axis that does not start at zero, figures that float instead of standing on a floor, decorations that add fake height, and a sneaky unit-conversion bug that shifts some heights by a quarter of an inch and not others. This post builds a small, framework-free JavaScript module for a height comparison to scale, with a node --test suite. Along the way it explains each failure mode and the test that catches it.

The original question is old, but the pattern keeps repeating. In September 2026 a developer posted their new height comparison site to the same subreddit and asked for brutally honest feedback, specifically: "Does the visual height difference look intuitive?" and "Do you notice anything that looks inaccurate or misleading?" The replies are a free QA report, and three of them are worth turning into requirements:

On the developer side, the parsing questions never stop. A Stack Overflow question asks how to convert 5'5" to centimetres when the data sometimes says 5' 5" with a space. An r/learnjavascript beginner tried to convert feet and inches to metres and lost the values to variable scope. And in r/FanFiction, someone wanted to line up 25 characters and found that every site capped the number of people.

So the requirements write themselves: accept the formats people type, refuse the ones that are ambiguous, never let a conversion drift, draw everyone on one floor with one scale, and be honest about what a silhouette can and cannot show.

Is this height comparison up to scale? The same 4'10" and 5'7" drawn three ways. Only the third panel, with an axis from zero and one shared ground line, is a height comparison to scale.

The truncated axis is the same mistake as a bar chart that does not start at zero. It is tempting because it makes small differences "readable," but in a height chart the visual ratio is the message. If you need to emphasize a 2 cm gap, add a zoomed inset or a number, not a cropped axis.

Height comparison to scale in JavaScript: storing Math.round(cm) and converting back to the nearest quarter inch shifts exactly the odd heights from 5'11" to 6'7" by 1/4 inch. Storing unrounded centimetres gives zero drift.

Let's start with the bug report, because it is the most instructive. I don't know how that site is built, but a very common pipeline reproduces the report exactly:

Run that for every inch from 5'11" to 6'7", and the heights that drift are 5'11", 6'1", 6'3", 6'5" and 6'7". Those are the odd ones, just as reported, with 6'5" going up a quarter and 6'1" going down a quarter (185.42 → 185 → 72.835 in → 6'0¾"). Even heights in that range happen to land within an eighth of an inch after rounding, so they look fine, which is exactly why this bug survives casual testing.

The inch is defined as exactly 2.54 cm, so there is no reason to lose information. The fix is a rule: pick one canonical unit, store it unrounded, and round only at the display edge. Centimetres as a JavaScript Number is fine; a double holds 180.34 to far more precision than a chart needs. If you persist to a database, an integer number of micrometres or a decimal column also works. Whole centimetres do not.

Height inputs arrive as 5'11", 5' 11, 5ft 11in, 71 in, 180 cm, 1.8 m, and the one that causes real trouble: 5.11. Is that 5.11 feet (about 155.8 cm) or 5 feet 11 inches (180.34 cm)? Users mean the second far more often, but silently guessing is how a 25 cm error ends up in a chart. My parser refuses it and offers a suggestion the UI can show as "Did you mean 5'11"?":

The 20–300 cm range is a product policy, not a fact about people. It matches the limits on Body Visualizer's height comparison tool, which also requires whole feet and inches below 12. Pick limits that suit your audience and test both edges.

Displaying feet and inches has its own classic bug: 5'12". If you compute feet with Math.floor and then round the remaining inches, 71.9 inches becomes 5 feet and 12 inches. Round the total first, then split:

denominator: 4 gives quarter inches; denominator: 1 gives whole inches. Because the input is the unrounded canonical value, formatFtIn(parseHeight("6'5\"").cm, { denominator: 4 }) returns 6'5" every time.

The difference readout should follow the same rule. I compute the percentage relative to the shorter person, which is how the Body Visualizer tool explains it too: 160 cm vs 175 cm is a 15 cm gap, and 15 / 160 = 9.375%. Whichever base you choose, state it in the UI, because "9.4% taller" and "8.6% shorter" describe the same pair.

The layout function is where "up to scale" is actually enforced. It computes a single pxPerCm from the tallest person plus some headroom, puts 0 cm on the ground line, and measures every figure from the same floor:

niceStep picks ruler intervals of 1, 2, 2.5 or 5 times a power of ten, so a chart of people gets 25 cm ticks and a chart that includes a building gets round hundreds:

The layout function is pure: give it heights and a box, get numbers back. That makes the "to scale" property directly testable, which matters more than any amount of visual review.

If you need many people, like the 25 fan-fiction characters, keep the same pxPerCm and let the chart scroll horizontally. Shrinking each slot until figures overlap, or splitting the cast into separately scaled charts, breaks comparability. If you do split, reuse one scale across every chunk.

Here is the subtle part behind the "circle" complaint. Most silhouette artwork has padding: transparent space above the head inside the image or SVG viewBox. Scale that asset to heightPx and the visible crown lands below the true height. Add a portrait circle above the head and the eye reads the circle's top as the person's top.

My silhouette path is authored in a unit box where y = 0 is the crown and y = 1 is the soles, with nothing above or below:

translate to the crown, then scale by the pixel height, and the feet land exactly on groundY. If you use richer artwork, measure its real bounding box once (for example with getBBox() in a build step) and normalize it to this convention. Keep names, portraits and badges outside the height box: below the ground line, beside the figure, or on the chest as that commenter suggested.
