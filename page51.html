Rotate a leaked API key without stopping your services: dotvault hands out the new value first

📅 Nov 09, 2026  |  Category: Technology  |  Read Source →

This is part 11 of the series "dotvault, Start to Finish: One Command from Your Laptop to CI, Your Team, and Your AI Agents." dotvault will be released free of charge when this series ends.

In the demo, a script kept calling with the key at 15-second intervals during the whole rotation, and in all 111 calls that got a response, the caller's value was accepted. The caller moved to the new value on its own, and the leaked value was rejected from then on.

That matters because rotating a key between two of your services has an ordering problem. Switch the service that checks the key first, and the caller still holding the old value gets rejected. Switch the caller first, and the checker rejects a value it has never seen. Either way, calls fail until the other side catches up, and the usual way around it is to stop both and switch them together. This part shows how dotvault rotate --reason leak avoids that.

This part also covers a second feature: rotating a key automatically at an interval you choose.

Rotation is not only for leaks. It is part of routine key management. Set an interval when you register a key, and dotvault keeps rotating it on its own, even when nothing has leaked. Nobody has to rotate keys by hand any more, so you can keep each key's lifetime short.

This follows part 4 (overwriting and rolling back values) and part 7 (creating service tokens). You can follow along without them.

The demo: order-worker processes orders and calls payment-api, the payment API. It sends PAYMENT_API_KEY, and payment-api checks that the value is right. Assume PAYMENT_API_KEY has leaked.

Rotation works for keys that both sides receive from dotvault, which means keys between your own services. dotvault generates the new value. An API key issued by another company's service has to be replaced in that service's dashboard.

In the demo project shop-backend, the first value of PAYMENT_API_KEY went into production with dotvault set. order-worker and payment-api each got a Read only service token. A service token is the string, starting with est_, that CI or a service uses instead of logging in. Part 7 shows how to create one.

Registering takes a token of the Credential rotation type. In Service Tokens, click Create token and pick "Credential rotation" as the Role.

As the dialog says, this token can issue tokens and register keys only inside one project and the environments you pick. It is not needed once the key is registered, so it expires in 1 day.

With that token, send one HTTP PUT, the request type that stores data at a URL. The body is JSON naming the holder and verifier tokens by Token ID.

HTTP 201 (created) and "created":true mean the key is registered. The fields:

key= in the URL is the key name, and project=, env= and file= say where it lives. $DOTVAULT_TOKEN in the Authorization header holds the Credential rotation token.

A rotation cannot start in the first 5 minutes after registering. Register service-to-service keys when you store them, not after a leak.

After registering, pull the same project as a person, with the holder token and with the verifier token.

Only the holder, order-worker, gets the value. This screen was captured after the rotation in section 4; a registered key is handed out the same way before and after a rotation. The person (an org admin) and the verifier see the key name in a "withheld 1 rotation-managed key(s)" warning, with no value. If you need a key with that name for local development, store a development value under a different key name.

The verifier does not pull. It reads the set of values it should accept from GET /v1/env/key-set. Each entry has the value, an ID for the value (keyId) and a state (state). The verifier accepts a value that is in this set.

A leak rotation cannot be stopped. --abort returns ABORT_REFUSED_LEAK with exit code 7, so there is no path back to the leaked value.

--status shows how far the rotation has got. In the audit log, the rotation reached STAGED in the same second it started.

The table leaves out LOCKED, the phase at the start (the audit log shows STAGED in the same second as the start), and VERIFIERS_OK, the mark that the verifier has read, which is recorded in the same second as PROMOTED.

The 15-minute waits exist because holders and verifiers may keep a value or a set they read for up to 5 minutes. Several instances can share one token and they do not all read at the same moment, so 10 more minutes are added. --reason leak does not skip these waits on its own. In a leak rotation, if one side never reads, the rotation moves on anyway after 30 minutes (plus the 5 minutes a read may be kept).

The console shows the rotation too. In the project's Keys, select PAYMENT_API_KEY and a Rotation section appears on the right.

Besides Phase, the Rotation panel shows when the rotation is next due to move on (Next due) and, in a leak rotation, when it moves on even if a side has not read the new value (Deadline). The figure leaves those two lines out.

After DONE, check the state and try writing the leaked value back.

In dotvault versions, the new v3 is state=current and the leaked v1 is state=revoked. v3 and v2 were made by system:rotation-driver, which is dotvault itself. v2 belongs to the routine rotation aborted in section 7.

Writing the leaked value with dotvault set, or rolling back to v1 with dotvault rollback --to 1, both fail with ROTATION_MANAGED: a key under rotation management changes only through rotation. As part 4 showed, an ordinary key can be rolled back to an old value after an overwrite. A key under rotation management cannot go back to the leaked value, even if someone tries with good intentions.

In the console's Audit Log, filter with shop-backend:production:env:PAYMENT_API_KEY as the Target ID: project, environment, file and key name joined by :.

The leak rotation's rows, from the bottom up. 14582408-… is the user ID of dev-e, the demo user.

A person started the rotation and dotvault did the rest. That the leaked value was revoked is one row you can point to later.

When nothing has leaked, a routine rotation runs without --reason (the same as --reason manual).

waiting on verifier payment-api means payment-api has not read the new value yet. last ok is when it last read the set. The phase deadline of a routine rotation (24 hours after the start) is how long it waits for a side that has not read the new value. Past it, the rotation does not move on; it stops (STALLED).

Even when nothing has leaked, you may not want to keep one key for a long time. Add interval_seconds (the rotation interval, in seconds) when you register the key, and dotvault starts a routine rotation on its own at that interval. Rotation stops being a person's job.

In the demo, a new key, WEBHOOK_SECRET, was registered with the same holder and verifier tokens as in section 1, with interval_seconds set to 600 (10 minutes). Ten minutes is only for the recording; in real use you would pick something like 30 days (2592000).

Right after registering, --status says managed but has never run: the key is registered but has never been rotated. Nobody typed a rotate command after that (the only thing running was the script that reads values). Once the 10-minute interval had passed, --status showed reason scheduled (dotvault started this rotation itself because the interval came round), and the rotation had already added the new value to the verifier's accepted set (STAGED).

The audit log agrees. After the registration (rotation_provisioner.config_created), both secret.rotation.started and secret.rotation.staged have the Actor system:rotation-driver. In the leak rotation in section 6, a person was the Actor of started; here dotvault started the rotation too.

A scheduled rotation is the same as the routine rotation in section 7: the old and new values both stay valid for at least 24 hours, and the new value goes to the verifier first, then to the holder. The next rotation starts once the interval has passed after the previous one finished. Right after you register a key, or shorten its interval, nothing starts for 5 minutes.

A rotation only reaches the end when the holders and verifiers read from dotvault as part of their normal work. If a service never reads again, the rotation waits on it with the waiting on … line from section 7, and past the deadline it stops (STALLED).

A rotation accepts the leaked value until the new one is everywhere. Even after the holder has read the new value, there is a 15-minute wait and the 60-second residual. To make the leaked value stop working sooner, skip the remaining waits with --revoke-now.

This was recorded after PAYMENT_API_KEY had been retired (later in this section), on a second key, REFUND_API_KEY, registered the same way. One of the script's calls already carried the new value (PROMOTED). Then --revoke-now: in the audit log, revoke_now, revoked and completed share the same second, and from the next call that got a response, the leaked value was REJECTED. The holder's value stayed accepted. The script ran 74 times during this recording, and in all 57 calls that got a response, the holder's value was accepted (the other 17 failed on the script's side before reaching dotvault).

Run --revoke-now once every holder has the new value, that is, after PROMOTED. It skips every wait from that point on, so if you run it earlier, dotvault switches values and revokes the old one without waiting for the verifier or the holder to read the new one, and a holder still on the old value is rejected.

The waiting on holder … line in --status is per token. When several services share one token, the line disappears as soon as one of them reads. Any other service still holding the old value is rejected after --revoke-now; that is what 10 of the 15 minutes of waiting are for. Run it only when you know every service has pulled again, for example after restarting them. In the demo the holder's value stayed accepted because there was one holder and it pulled on every call.

One more thing: revoking takes the value out of dotvault's accepted set. While a verifier keeps its copy of the set (up to 5 minutes), it may still accept the leaked value. The demo's verifier read the set on every call, so the leaked value was REJECTED from the next call.

--confirm repeats the key name; one wrong character stops it with VALIDATION_ERROR and nothing is sent. Only a signed-in person can run it; a service token cannot.

If you cannot even wait for the holder to move to the new value, retire the key.

The retire ran on the same key after the PAYMENT_API_KEY rotation was recorded. revoked version(s): 3 means it revoked v3, the current value from the rotation; v1 and v2 were already revoked. The verifier can no longer read the set (HTTP 403, NOT_BOUND), and writing the leaked value back with set fails with VALUE_REVOKED: a revoked value can never be written again.

Retire hands out no new value, so the holder and the verifier both stop at once. --confirm repeats the key name, and one wrong character means nothing happens. Only a signed-in person can retire; a service token cannot. Use it only when the leaked value has to stop working right now, even at the cost of stopping your services.

For a routine rotation when nothing has leaked, use dotvault rotate (--reason manual); the old value stays usable for at least 24 hours. Add interval_seconds to the registration, and dotvault starts that routine rotation on its own at the interval you set.

Rotating a key between two services fails calls whichever side you switch first, until the other side catches up. Register service-to-service keys for rotation management when you store them, and when one leaks, run dotvault rotate --reason leak. dotvault gives the new value to the verifier, then to the holder, and revokes the leaked value only after both have read the new one, so the leaked value stops working without stopping your services. Set an interval when you register the key, and routine rotation before any leak stops being a person's job too.

The Two Scripts Cloudflare Appends to Every One of Our 56 Pages: 1,239 Bytes of Email Decoding and a 31,853-Byte Analytics Beacon

📅 Nov 09, 2026  |  Category: Technology  |  Read Source →

Our sitemap lists 56 URLs. I fetched every one of them once and read the HTML the server returned. Two of the script tags in each document are not ours: the edge appends them, and they are identical on all 56 pages.

The first is Cloudflare's email decoder, served from our own host at /cdn-cgi/scripts/5c5dd728/cloudflare-static/email-decode.min.js. It answers HTTP 200, carries 1,239 bytes and is served as application/javascript. Its tag is exactly this:

There is no integrity attribute on it and no crossorigin attribute - just data-cfasync="false", which tells the browser it may be fetched without blocking the parser.

The second is Cloudflare's analytics beacon, which lives on a host that is not ours: https://static.cloudflareinsights.com/beacon.min.js/vce701823e78c4301a35b7e07294d87301792088814092. It answers HTTP 200 with 31,853 bytes, served as text/javascript;charset=UTF-8. Its tag carries four things at once: type="module", crossorigin="anonymous", an integrity attribute with a sha512 hash, and a data-cf-beacon payload.

The payload has exactly four keys: r, spa, token, version. The version reads 2024.11.0, r reads 1, spa reads 2, and the token is 32 hex characters. It is the same payload on all 56 pages - one variant, not 56.

Because the beacon tag carries a sha512 hash, I hashed the 31,853 bytes Cloudflare served and compared the digest with the one in the tag. They are the same string, so a browser that checks the hash finds a match.

Both edge scripts come after the closing footer tag and before the closing body tag on all 56 pages. The rest of the document is ours: 155 script tags across the fleet, and not one of them carries an integrity attribute.

All 56 responses carry the same Content-Security-Policy header, and the same script-src directive. That directive lists 7 tokens: 'self', one sha256 hash, 'wasm-unsafe-eval' and 4 host names.

Neither edge script is named there. The beacon's host, static.cloudflareinsights.com, is not in script-src on any of the 56 pages, and the path the email decoder is served from is not named either - it is same-origin, so 'self' covers it.

We did not open these pages in a browser and we did not run any of this JavaScript, so we are not going to claim what a browser does with the beacon tag. This is a report of what the header and the markup say.

One build, one day, one fetch per URL, plain HTTPS from one network, signed out. The 56 URLs are the ones in our sitemap and are not an inventory of the site. We did not measure the browser's view of any of this, did not compare against another build, and did not look at any analytics data. The 33,092 bytes are the sizes of the two files as served over the wire, not their size on disk.

We Built Opsville, a Free Pixel-Art Town Where You Fix DevOps Incidents

📅 Nov 09, 2026  |  Category: Technology  |  Read Source →

Opsville is a small pixel-art town where every district is broken, and you are the one on call. 🏘️ Each district is one DevOps topic: Linux, Docker, Git, CI/CD, Kubernetes, monitoring, security and databases. The people there hand you quests. Most quests open one of our browser simulators, then ask three questions. Fix all eight districts and the town gets its Launch Day.

It is free, it runs in your browser, and you can play it now at devops-daily.com/opsville.

Disclosure: we build Opsville at DevOps Daily. It is free and needs no sign-up.

Handy keys: Q for quests, M for the map, P for your profile, H for help, F for photo mode, and 1 to 4 for emotes.

There are 8 districts and 34 quests. Progress saves in your browser, so you can close the tab and come back later.

From Docker Docks on, each district ends with a boss, which opens after the quests before it. The boss quiz plays as an incident: a status board with three systems that go from Down to Fixed as you answer.

In Docker Docks the board shows the container runtime, the host kernel and the image registry. In Git Garden it is the main branch, the release tags and the team clones. In the Observatory it is checkout, the status page and the on-call channel. Get two of the three questions right and the incident closes. Sophia at the Docks sums it up: "Every container stays in its box. Incident closed."

Once you clear Linux Lodge, the pager starts. It stays quiet for the first three minutes, then pages you every 6 to 10 minutes, never while a panel is open. Each page comes from a district you have already opened:

Press On my way and you have two minutes to get there and 30 seconds to fix it. You see the symptom (df -h shows / at 100%, and /var/log/app.log is 38 GB and growing) and three possible fixes. Pick "Reboot the server" and the game tells you why that fails: the disk is still full after a reboot, and the log keeps growing. The right fix is to truncate the log and set up logrotate.

There are ten pages across the eight districts, from a container stuck in a restart loop to an expired TLS certificate. If the pager gets too much, snooze it for 15 minutes or turn it off in Help.

Twelve lost packets are hidden around town, and each one has a short story. "A DNS query from 2009" is still waiting for an answer. "A retry with no backoff" tried 9,000 times a second and is tired now.

Find all twelve, and an old hatch by the lake in the town square opens. Below it is a basement full of blinking racks and one terminal:

It is the oldest server in town, ten years without a reboot. Finding every packet also gets you the golden packet cap.

Vite, TypeScript and Phaser 3. Phaser draws the world: the map, the people, the weather and the effects. The panels, quizzes and HUD are plain DOM on top of the canvas.

Maps from text. The whole world is one text file of 72 x 50 characters, where one character is one 16 x 16 tile. A build script turns it into Tiled JSON with ground, decor, collision and object layers. Three rows from the top of the map:

P is a pine, : a stone path, g a grey roof, S a stone wall, D a door and H a castle wall. Moving a building is a diff you can review.

Static files on Cloudflare Pages. The game builds with the base path /opsville/. A release script copies the build into our main site, and Cloudflare Pages deploys it with everything else. The game needs no server of its own.

XP that the server decides. Sign-in is optional, with a free DevOps Daily account. When you are signed in, the game only tells our learning platform's API "I finished quest X". The API looks the quest up in its own list and decides the XP. Each quest counts once per player, two quests must be at least 30 seconds apart, and one player can count at most 24 quests in 24 hours. A test in the game fails when its quest list drifts from the server's list, so the weekly leaderboard stays fair.

The launch post has the rest of the build story: how a simulator in a frame tells the game you finished, and how we made two art sources look like one game.

Start in Linux Lodge and see how far you get before the pager goes off: play Opsville free.

By reverse engineering the 2014 Renault Latitude’s firmware and exploiting some vulnerabilities, the researcher fixed their daylight savings time mismatch issue.

When you purchase through links on our site, we may earn an affiliate commission. Here’s how it works.

A security researcher has revealed how they were forced to update the time on their car infotainment system using reverse engineering techniques. Of course, invasive tech surgery shouldn’t be needed for this kind of basic routine daylight saving time tweaking task. However, Rasmus Moorats’ 2014 Renault Latitude wouldn’t allow him to adjust the time because the original navigation map SD card was missing.

Moorats had been warned. When he bought the used car, the previous owner noted that the SD card would be required to change the time on the in-car display. “I didn't really find that believable,” recalls the security researcher. They seem to have believed it was a skill issue of the prior owner and, because the maps it contained were chronically out of date, they decided to confidently decide they didn’t need the SD card...

The time to adjust non-connected clocks to daylight saving time inevitably came, and Moorats decided to adjust the in-car time display, which had become an hour out of sync. Two settings menus were available via the in-dash system. One allowed the adjustment of Bluetooth and Phonebook settings – clearly no use here. But the second settings menu wouldn’t produce any submenu. Instead, an error message "No maps detected!" popped up every time it was prodded.

With a certain set of skills under his belt, Moorats decided to “just RE it,” where RE = reverse engineer. He found out that the head unit ran a customized Linux-based TomTom operating system on a Samsung SoC. In brief, he extracted and analyzed the firmware, built a QEMU environment for the device, reversed the scripting engine, and uncovered a number of vulnerabilities affecting the system.

The breakthrough came in a brainwave, which seems to stem from experience with kernel exploit techniques during his day job. “Instead of trying to get the userland to execute our script, why don't I get the kernel to execute our script instead?” pondered Moorats. The approach worked, rewarding Moorats with root-level access to the infotainment system.

The 2014 Renault Latitude owner subsequently discovered that the date & time settings were in /mnt/flash/settings.dat in a custom binary format. Interestingly, the system “doesn't really have a concept of time zones at all,” observed Moorats in the conclusion of his blog post. “It gets the time from GPS and stores the local offset as a number of minutes. Mine was set to 180. I changed it to 120.”

The University of Texas MD Anderson Cancer Center is expanding its cancer care facilities through the addition of two new buildings—totaling a $3.4 billion investment.

The new facilities, dubbed Inspiration Tower and Prism, will make up nearly two million square feet and allow for MD Anderson to care for nearly 250,000 patients annually, executives say. The expansion is funded by UT MD Anderson and its philanthropic support.

“Every detail of these buildings, from the technology to the treatment rooms, was designed around our patients who will receive their care in them and our employees who will work in them,” said Jeffrey Lee, M.D., UT MD Anderson president ad interim, in a statement. “The facilities will serve as a physical representation of hope for the patients and their families who will walk through the doors.”

Singapore-based cloud computing company MegaSpeed is in the international spotlight after Nvidia CEO Jensen Huang admitted to being unfaithful to his wife, following reports linking him to MegaSpeed executive Alice Huang.

U.S. intelligence officials believe she is a Chinese intelligence asset, according to The New York Times.

While the Nvidia CEO — one of the world's most prominent executives and a figurehead of the AI industry – did not name MegaSpeed or Alice Huang in his statement, he acknowledged his infidelity and said Nvidia's Board of Directors had begun an independent investigation "regarding the national security concerns raised in news reports."

"I support the investigation and will cooperate fully. I love our country and our company. I am committed to protecting NVIDIA and supporting America's national security. I am proud and grateful to be an American," he said.

Nvidia said in a statement it had "no reason to believe that either national security or NVIDIA secrets were compromised," but that its "Board's inquiry will examine all available information."

Tech darling Nvidia sells advanced AI and data center chips and has customers including Microsoft, Amazon, Google, Meta and Oracle. The explosion in AI adoption in recent years has fueled its stock and pushed it to a $5 trillion market cap this year.

MegaSpeed sells services to Asia Pacific-based companies that need large amounts of computing capacity, usually for AI projects, by selling access to computing resources hosted in data centers in Southeast Asia.

It advertises itself as a "core business partner" of Nvidia's computing power cloud business in the region, allowing customers to rent computing power from Nvidia GPUs, or "graphics processing units" — specialized chips designed to do many calculations at the same time.

The service allows businesses to complete costly AI operations without buying and operating all the hardware themselves. It can also give customers remote access to computing power from advanced chips located outside China. U.S. controls restrict the export of some advanced chips to China, but remote access is a separate question.

MegaSpeed, which has offices in Singapore and Indonesia, has previously faced media and government scrutiny over whether some of its GPUs have been redirected to China, which is subject to U.S. export controls on some advanced chips.

A report published by Bloomberg in December 2025 stated that the U.S. government was investigating Megaspeed's ownership structure and whether it had smuggled Nvidia chips to China.

A response to the article published on MegaSpeed's website said it contained "misleading information and incorrect insinuations." It added that inspections by the Bureau of Industry and Security of the U.S. Commerce Department, the Ministry of Investment, Trade and Industry of Malaysia, and Nvidia had found "no evidence of any violations concerning the illicit transfer of chips or any illegal activities."

Businesswoman Alice Huang is an "executive" at MegaSpeed and a "publicly reported Chinese intelligence asset," according to a House Select Committee on China statement on Nov. 5. Committee heads have requested Jensen Huang's attendance at a Nov. 18 briefing to establish "the extent to which U.S. national security has been placed at risk" after reports raised "significant national security concerns regarding [China's] access to sensitive U.S. technology and information."

According to New York Times reporting this month, Alice Huang is a Chinese citizen who speaks good English and is well-connected among high-ranking chip industry executives.

The Times reported on Friday that a memo was distributed among policymakers in the Trump administration last spring identifying a Chinese businesswoman with a close relationship to Jensen Huang as passing information about U.S. AI chips to Beijing's top spy agency and seeking policy influence.

Bloomberg reports that Alice Huang also goes by Huang Le and helped set MegaSpeed up. Bloomberg previously listed her as one of the people collaborating with a Singapore police investigation into the company's activities in relation to China. Singapore's government has said it had not investigated Alice Huang's alleged intelligence ties or her relationship with Jensen Huang.

CNBC has contacted MegaSpeed for comment.

The reports about the relationship prompted renewed scrutiny of Jensen Huang's past comments on engaging with the Chinese market. He told CNBC's Arjun Kharpal on Oct. 22: "No market is closed forever, and China wants foreign companies to invest in China, just as Germany wants foreign companies and countries to invest in Germany."

"And so the market has to be open and it has to be welcoming. There's no reason to believe that market is going to be closed to the best competitors in the world, and Nvidia is surely the best in the world at doing what we do."
